# 25 · 启动加速与配置热更新(服务端 5.1)

## 问题

数据库几十万条记录时,每次改配置、重启服务都要等好几分钟(3.4.6 里只是把管理程序的等待时间加到 10 分钟)。

原因:服务每次启动在开始监听之前,先做了三件事,每件都要读完整个数据库:

1. `PRAGMA integrity_check`(完整性检查);
2. 搜索索引的内部检查 + 把 `media` 和 `media_fts` 逐行比对;
3. 打开后又做了一遍搜索索引检查(同样的比对);

之后还要同步地整理所有对话的计数。账号命令(`mediahub user …`,管理程序频繁调用)也走同一套检查。

## 做法

### 1. 只在需要时才做完整检查(store/guard.go)

数据目录里记一个 `session.state`:服务运行时是 `running`,**正常退出**后改成 `clean`。启动时:

| 情况 | 动作 |
|---|---|
| 上次是 `clean`,没有登记检查 | 快速打开(只做迁移),几百毫秒 |
| 上次是 `running`(崩溃 / 被强杀 / 断电) | 完整检查 + 必要时自动修复 |
| 没有状态文件但有数据库(旧版本升级上来第一次) | 完整检查一次 |
| 存在 `needs-check.flag`(运行中发现损坏、后台检查失败时登记) | 完整检查,通过后清掉 |
| 环境变量 `MEDIAHUB_CHECK_DB=1` | 强制完整检查 |

运行中每 7 天(`dbMaintenance`)用一个只读连接做一次 `PRAGMA quick_check`,不开事务、不挡请求;发现问题登记 `needs-check.flag`,下次启动检查并修复。

实测(合成库,40 万条媒体 + 搜索索引):完整检查启动 10.3 秒,快速启动 1 毫秒,后台 quick_check 1.6 秒(不挡服务)。真实库行更大、索引更多,差距更大。

### 2. 对话计数整理放到后台

`Finalize` 改成后台 goroutine(按根目录加锁,和扫描互斥),不再挡着开始监听。

### 3. 配置热更新(cmd/mediahub/reload.go)

`POST /api/v1/admin/config/reload`(管理程序保存后调用)和手机端保存配置都会触发:重新读取配置文件,和正在用的比较(`config.Diff`),然后

| 设置 | 处理 |
|---|---|
| `log.level` | 立刻改日志级别 |
| `priority.*` | 调度器换配置(`Governor.Reconfigure`),不重启 |
| `tunnel.*` | 只重启内网穿透模块(frpc 进程),服务和数据库不动 |
| `update.*` | 只换自动更新模块 |
| 浏览历史、转码上限、存储优化、图片转换等**开关和数字** | 读取它们的地方每次都看当前值,原地改(`config.CopyScalar`);字符串不在内,改字符串不是原子的 |
| 其余(监听地址、HTTPS、媒体目录、缓存、账号、各种路径、字符串类转码设置) | 返回 `restartRequired` 列表,提示重启 |

返回 `{changed, applied, restartRequired}`。管理程序据此只在真正需要时才显示"重启服务"横幅,并列出具体是哪几项。

## 实时延迟(tunnel/latency.go)

有人在看时(管理程序穿透页、手机连接质量页,每次轮询带 `watch=1`)每 2 秒采样一次,40 秒没人看就停:

- `chainMs`:通过外网地址在保活连接上请求 `/api/v1/server/info`,量往返(建连耗时不算);
- `serverMs`:到 frps 的 TCP 连接耗时(kcp / quic 的 UDP 控制端口量不到时为空)。

接口:`GET /api/v1/admin/tunnel?watch=1`(管理程序)和 `GET /api/v1/server/link?watch=1`(登录用户,不含地址 / 令牌)。
