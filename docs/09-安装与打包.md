# 09 安装与打包

打包产物都在项目的 `dist\` 目录,由 `tools\package.ps1` 一键生成(每次只保留当前版本,历史版本会被清掉)。

| 文件 | 说明 |
|---|---|
| `MediaHub-<服务端版本>-portable.zip` | 服务端 + 桌面管理程序的**便携版**(不再提供安装包):解压即用,放在 NAS 任意目录 |
| `LocalBrowse-<手机端版本>.apk` | Android 手机客户端(已签名的发布版,Android 8.0+) |
| `SHA256SUMS.txt` | 校验和 |

## 一、NAS(Windows)上安装服务端

1. 解压 `MediaHub-<版本>-portable.zip` 到 NAS 上任意目录,双击 `MediaHub.exe`。
2. 打开 MediaHub:
   - **媒体库** 页直接选盘符(比如 `D:\`、`E:\`),可给每个盘起一个短名字(手机上显示为分组标签);盘符下每个母文件夹是一个群,规则见第六节。
   - **账号** 页创建登录手机用的账号和密码。
   - **概览** 页点「启动服务」。第一次启动会先扫描并读取元数据,大库需要几分钟到几十分钟。
3. **防火墙**:第一次启动时 Windows 可能弹出防火墙询问,选择允许「专用网络」。若没弹窗,手动放行 TCP 端口 8480(默认,可在「网络」页修改)。
4. 记下「网络」页里列出的本机局域网地址,例如 `192.168.1.20:8480`。

服务由管理程序启动后独立运行,关掉管理界面不影响手机访问。

安装包里已包含 `ffmpeg / ffprobe / ExifTool`(读取拍摄时间、尺寸、生成视频封面),不用另外安装。

### 可选:Jellyfin(视频转码与现成封面)

不装 Jellyfin 也能浏览、播放手机能直接解码的视频。需要转码(比如 mpg/wmv/杜比视界)或想复用 Jellyfin 已生成的封面时:

1. 自己安装 Jellyfin(便携版或安装版均可),让它只监听本机 `127.0.0.1:8096`,并把同样的媒体文件夹加为它的媒体库。
2. 在 Jellyfin 管理后台创建一个 API 密钥。
3. 在 MediaHub「视频转码 → Jellyfin」页填入地址和密钥。
4. Intel 核显转码(QSV)要在 NAS 的 BIOS 里保持核显启用。转码功能本身是下一阶段(M3)的内容。

### 数据放在哪里

- 数据库、日志:默认 `C:\MediaHub\data`(建议放固态盘,可在「存储」页修改)。
- 配置:安装目录下 `runtime\mediahub\config.json`。升级安装不会覆盖它。
- 视频封面缓存:放在每个媒体盘根目录的隐藏文件夹 `.mediahub`(每盘上限默认 50 GB,空间不够时自动改放安装目录的 `runtime\cache`)。**服务端除了这个缓存目录,不会往媒体盘写任何东西。**

## 二、手机安装

1. 把 `LocalBrowse-1.1.1.apk` 传到手机(数据线、局域网共享、聊天软件均可),点开安装,允许「安装未知来源应用」。
2. 首次打开会请求「附近设备 / 本地网络」权限,**必须允许**,否则 Android 17 连不上局域网地址。
3. 输入服务器地址(如 `192.168.1.20:8480`),点「连接」,再输入账号密码登录。

升级时直接覆盖安装即可(签名一致,数据保留)。

## 三、手机端设置一览(列表页左上角菜单 → 设置)

- **外观**:跟随系统 / 浅色 / 深色;聊天背景(渐变 / 纯色);日期胶囊开关。
- **浏览**:记住每个文件夹的浏览位置;聊天流最新在底部;网格默认列数;快速滑动时暂停加载缩略图。
- **图片**:磁盘缓存上限(128 MB–4 GB)、内存缓存比例、硬件位图、淡入动画(重启生效)。
- **视频播放**:自动播放、循环、静音、默认倍速、记住播放进度、快进快退步长、画面缩放、控制条隐藏时间、屏幕常亮、播放技术信息(解码器 / 码率 / 丢帧)。
- **编解码器**:解码方式(自动 / 硬件优先 / 软件优先 / 仅硬件 / 仅软件)、解码失败自动改软解、备用解码器、MediaCodec 异步队列、隧道播放、缓冲大小、最大分辨率 / 码率(给转码用)、首选音轨语言、内嵌字幕;并可查看**本机解码器列表**(每种格式的解码器、硬件 / 软件、最大分辨率)。
- **网络**:连接超时、读取超时。
- **存储与缓存**:清除图片缓存、清除浏览位置、清除播放进度、恢复默认设置。
- **服务器与账号**:当前服务器、退出登录。

## 四、自己重新打包

```powershell
powershell -File tools\package.ps1                # 全部(服务端测试 → 安装包 → 便携版 → APK)
powershell -File tools\package.ps1 -SkipAndroid   # 只打桌面端
powershell -File tools\package.ps1 -SkipDesktop   # 只打安卓端
```

- 前提:已运行过 `tools\setup.ps1`(便携工具链)。桌面端打包需要 Rust(MSVC)与 Node,NSIS 工具已缓存在 `%LOCALAPPDATA%\tauri\NSIS`。
- Android 发布签名:密钥库与口令在 `signing\`(`localtg-release.jks`、`keystore.properties`),**请自己备份且不要外传**;丢失后新 APK 无法覆盖安装旧版。没有 `signing\` 时 release 改用调试签名。
- 版本号要同步改:`android\app\build.gradle.kts`(`versionName` / `versionCode`)、`server\cmd\mediahub\main.go` 的 `version`、`desktop\package.json`(及 `package-lock.json`)、`desktop\src-tauri\Cargo.toml` / `tauri.conf.json`、`tools\package.ps1` 的 `$Version`(手机端版本;该文件需保持 UTF-8 BOM)。服务端 / 管理程序的版本号取自 `desktop\package.json`,包名是 `MediaHub-<该版本>-portable.zip`(可用 `-ServerVersion` 覆盖)。

## 五、已知限制(1.1.1)

- 安装包没有数字签名,Windows SmartScreen 可能提示「未知发布者」,点「更多信息 → 仍要运行」。
- 安装包不含 libvips:HEIC / RAW 等由 ffmpeg / ExifTool 转换,**JXL 需要 libvips**(可选,放到 `tools\vips\bin\vips.exe` 即可,不放则 JXL 在手机上无法显示)。
- 视频转码:服务端内置 ffmpeg 转码(不依赖 Jellyfin),配置了 Jellyfin 且已收录该视频时优先用 Jellyfin。手机能直接解码的视频不经过转码。
- 手机端颜色和圆角是按 Telegram 近似调的,需要在真机上再微调。
- 模拟器的软解码器能力有限(例如 1080p60、HEVC Main10),真机以硬解为准。
- 手机让 Windows 防火墙放行端口:管理程序「网络 → 开机与防火墙」有一键放行(会弹 UAC 确认)。

## 六、文件夹如何变成群组(0.3.0 起)

- 在 MediaHub「媒体库」页**直接选盘符**(例如 `D:\`、`E:\`)。盘符本身是手机上的一个分组标签(顶部的 `D:` / `E:`)。
- 盘符下的每个**母文件夹**是一个群,群名就是文件夹名。
- 母文件夹里无论嵌套多少层子文件夹,都**不再单独成群**:里面所有的图片和视频平铺进这个母文件夹的群里(按时间排序)。
- 直接放在盘符根目录的媒体,归入以盘符命名的群(没有就没有这个群)。
- 空文件夹、只含非媒体文件的文件夹不显示。
- 母文件夹或子文件夹改名、文件在子文件夹之间移动,群和媒体的 ID 都不变,手机上记住的浏览位置不丢;文件从一个母文件夹移到另一个母文件夹,会换群。
- 升级到 0.3.0 及以后版本后第一次启动会自动重新扫描并按新规则分组,不需要手动清理。

## 八、界面动画

设置 → 外观 → 界面动画:

- **滑动 + 视差**(默认):新页面从右侧整屏滑入,旧页面后退 1/4 屏,返回时反向;支持 Android 的预测性返回手势。
- **Material 共享轴**:位移约 1/10 屏宽 + 淡入淡出(Material Motion 规范)。
- **仅淡入淡出**、**关闭动画**。
- 点开图片 / 视频时,缩略图直接放大成全屏(共享元素,容器转换),返回时缩回原位;聊天流与网格切换使用淡入加轻微缩放;登录与列表之间使用 fade through。

## 九、日志与问题反馈

手机端 设置 → 日志与诊断:

- 日志级别:关闭 / 仅错误与警告 / 信息(默认)/ 调试(含每个网络请求和播放器事件)。
- 应用崩溃时会自动保存崩溃报告(堆栈、设备信息、最近日志、系统 logcat),**下次启动弹出"上次异常退出了"**,可一键分享或复制。
- 「分享日志文件」打包成 zip(设备信息、应用日志、崩溃报告、logcat)用系统分享发出;「复制最近日志到剪贴板」可直接粘贴到聊天里。
- 「查看日志」可在应用内直接看,支持只看警告和错误。
- 遇到问题:先把日志级别调到"调试",重现一次,再分享日志。

服务端日志在 `C:\MediaHub\data\logs\`(管理程序「日志」页可查看)。

## 十、扫描:续扫、跳过、实时速度(0.4.0)

- **实时速度**:管理程序「概览 → 索引进度」每个盘显示实时速度——扫描阶段是"xxx 文件/秒",读取元数据阶段是"已读 N / 总数 · xx 个/秒 · 预计还需 x 分钟"。速度由服务端每秒采样并平滑。
- **扫到一半关闭,下次接着扫**:每个母文件夹扫完就会记一笔,服务再次启动时只扫没扫完的母文件夹,并提示"接着上次中断的扫描继续";元数据读取和封面预热本来就只处理没做完的部分。
- **完整扫描过的盘,启动时不再重扫**:距上次完整扫描不足"启动时复用上次扫描的时限"(默认 12 小时,「媒体库 → 扫描与过滤」可改,0 = 每次启动都扫)就直接跳过。新添加的盘、被中断的盘、超过时限的盘仍会扫描。
- **定时重新扫描**:服务运行期间每隔"定时重新扫描间隔"(默认 24 小时,0 = 不定时)自动扫一遍,发现新增、删除和改名。
- **手动「重新扫描」**:丢弃中断记录,从头完整扫一遍。
- **从旧版本升级**:数据库启动时立即把旧版"每个文件夹一个群"的数据整理成"母文件夹一个群"(子文件夹的群被删除,媒体并入母文件夹),不用等扫描;接口也只返回母文件夹。

## 十二、1.0.0 新增

### 视频与图片
- **服务端转码**:手机解码不了的视频,播放器报错后自动改走 Jellyfin 的 HLS 转码(QSV 硬件加速),也可在播放器「更多 → 画质 / 转码」手动选 1080p / 720p / 480p。服务启动时自动在 Jellyfin 里为每个盘创建媒体库(名称 `MediaHub <盘符>`)并同步硬件加速设置;退出播放会通知服务端停止转码。
- **服务端图片转换**(`render`):HEIC / HEIF / AVIF、RAW(内嵌预览)、TIFF 等手机无法显示的格式由服务端转成 JPEG。设置里「HEIC 显示方式」可选手机本地解码或服务端转换。

### 损坏 / 不完整文件的识别
- 之前"很多视频打不开、没有预览图、播放一半报错"的原因是 **NAS 上的文件本身不完整**(下载中断留下的 0 字节或被截断的文件),不是网络问题。
- 服务端扫描时检查 MP4 / MOV 的结构(顶层 box 超出文件末尾、缺少 moov 即判为不完整),0 字节文件直接标记。接口给每个条目带 `flags.corrupt / flags.truncated` 和中文原因 `problem`。
- 手机端:损坏的文件显示警告图标和"文件损坏 / 空文件"占位,不再是一块空白;不完整的视频带"不完整"标签,点开后提示"播放到被截断处会停止";错误提示翻译成人话(下载中断、文件已不存在、登录失效、网络问题等);完全损坏的视频不创建播放器,可选"仍然尝试播放"。
- 快速滑动时被暂停的请求(本地返回 504)不再记成错误。

### 服务端日志与目录读取失败
- **日志系统**(`internal/logx`):写到 `<数据目录>\logs\mediahub-日期.log`,单个文件超过 20 MB 自动切分,保留最近 14 天且总量不超过 300 MB;内存里留最近 3000 行;`stderr.log` 记录运行时致命错误。
- **崩溃捕获**:所有后台协程和 HTTP 请求里的 panic 都被捕获,记日志并写 `crash-时间.txt`(堆栈、运行环境、最近 300 行日志),服务继续运行;主流程崩溃也会先写报告。
- **日志级别**:管理程序「日志 → 日志设置」可选 调试 / 信息 / 警告 / 错误(默认信息),修改后重启服务生效。
- **管理程序「日志」页**:按级别过滤、关键字搜索、颜色区分、停在底部时自动跟随;「导出日志包」把全部日志和崩溃报告打成 zip(不含密码、令牌和 API 密钥),服务没运行也能导出;列出崩溃报告,一键打开。
- 日志接口(`/api/v1/admin/logs`、`/logs/bundle`、`/logs/level`)只接受本机回环地址 + 管理密钥,普通用户令牌不能访问。
- **目录读取失败分类**:概览页每个盘的"跳过 / 失败的目录"可展开,按原因分为 没有权限(系统保护目录,正常)、已不存在(被删除,正常)、盘不可用(移动硬盘断开、网络盘掉线)、读取出错(硬盘坏道)等,附 Windows 错误码。系统保护目录(`System Volume Information`、`$RECYCLE.BIN`、`Recovery` 等)总是跳过,不再产生"读取失败"。

### 桌面管理程序
- 托盘菜单增加「启动服务 / 停止服务 / 重新扫描媒体库」。
- 「网络 → 开机与防火墙」:开机自启(写当前用户的 Run 注册表项,启动后只留托盘)、"打开管理程序时自动启动服务"、防火墙状态检测与一键放行(UAC)。

### 手机端
- 令牌改为 Android Keystore 的 AES-GCM 加密存储;旧版本留下的明文令牌升级后自动转为密文。
- 聊天页「更多 → 跳转到日期…」(按时间排序时):选一个日期,列表重建并停在该日附近。
- 查看器「保存到手机」(图片顶栏按钮、视频更多菜单):原文件保存到 图片/MediaHub 或 影片/MediaHub,相册里可见(Android 10+ 不需要存储权限)。

## 十三、1.1.0 新增

### 加密传输(HTTPS)
- 手机与服务器之间默认走 **HTTPS**:服务端第一次启动时生成一张 ECDSA P-256 自签名证书(10 年,存在数据目录 `tls-cert.pem` / `tls-key.pem`),TLS 1.3 + HTTP/2(Go 会按手机有没有 AES 硬件加速自动选 AES-GCM 或 ChaCha20-Poly1305),握手快、吞吐高。
- **证书固定**:手机第一次连接时先读取服务器证书的 SHA-256 指纹并显示出来,请和管理程序「网络 → 证书指纹」显示的核对,一致再点「信任并连接」。以后手机只接受这张证书(不依赖 IP,换 IP 也能连);证书变了(服务器重装 / 被冒充)会拒绝连接并提示重新核对。
- 管理程序走**仅本机的明文端口**(监听端口 + 1,例如 8481,只监听 127.0.0.1;可用 `adminListen` 改),不必处理自签名证书。对外的 8480 是 HTTPS,明文访问会返回 400。
- 可在「网络 → 监听与访问」关闭加密传输(退回明文 HTTP,不推荐)。
- 从旧版本升级:手机上旧的 `http://` 登录会被识别为失效,弹出登录页并提示重新连接、核对指纹。
- 登录令牌继续由 Android Keystore 加密保存。

### 转码不再依赖 Jellyfin
- 原因:真机上点「转码」一直报 503 —— 你的 NAS 没配置 Jellyfin,服务端返回"未启用转码"。
- 现在服务端自带 **ffmpeg HLS 转码**(`internal/api/hls.go`):先按视频总时长生成完整的 VOD 播放列表(4 秒一段),段在手机请求到时才由 ffmpeg 现转;拖动进度条 / 从上次位置继续 / 回看都会从对应的段重新启动 ffmpeg(精确定位),时间轴和原视频一致。
- 英特尔核显 QSV 硬件编码(`h264_qsv`,必须加 `-forced_idr 1`,否则关键帧不按 4 秒对齐),失败自动退回 libx264 软编;同时转码路数受「同时转码路数」限制;转码进度领先播放太多会自动暂停,退出播放 / 空闲 90 秒清理临时文件。
- 配置:「视频转码 → 转码引擎」选"自动"(有 Jellyfin 且已收录该视频就用它,否则内置)或"只用内置 ffmpeg"。

### 重新添加文件夹不再重扫
- 配置里移除的盘 / 文件夹只是"停用"(手机上不再显示),索引数据保留;再次添加(路径不区分大小写)时直接复用,启动时不重新扫描(需要时点「重新扫描」)。盘换了(卷序列号变化)则旧数据作废,重新扫描。
- 从 0.4.0 之前的版本升级:数据库迁移 v6 把"已有索引数据"的盘标记为已完整扫描过,升级后不会整盘重扫。

### 目录读取错误 123
- "文件名、目录名或卷标语法不正确(错误码 123)"多半是文件夹名以空格 / 点结尾,或是 Windows 保留名(CON、NUL、COM1……)、含 `? * :` 等字符(Linux / Mac 创建的)。Win32 普通路径会把这些名称"规范化"掉,于是找不到目录。
- 现在遇到这类错误会自动改用**扩展路径(`\\?\` 前缀)**重试,读目录、读文件、取元数据、转换图片、转码都支持;仍然失败的目录归为"名称不合法"(跳过,概览页可展开看到路径和原因,改个名字即可)。
- 顺手修了一个旧 bug:超长路径(≥240 字符)的扩展路径前缀写成了 `\?\`(少一个反斜杠)。

### 返回动画
- 研究了几个开源实现:Telegram(`ActionBarLayout`:上层页面 1:1 跟手、下层页面静止 + 变暗、左边缘投影、松手按位置 / 速度判定、ease-out-quint 收尾)、Voyager 的预测性返回(`SeekableTransitionState` + 手势进度映射)、Navigation Compose 2.10 的 `predictivePopEnterTransition / predictivePopExitTransition`(参数是手势起始边)、Navigation 3 的 `predictivePopTransitionSpec`。
- 发现的问题:① 手势返回没有自己的规格,导航库的默认预测性动画是"页面缩成一张卡片 + 淡出",和按钮返回的滑动完全不一致,松手后还会停一下再消失;② 手势进度是按"播放进度"去 seek 动画的,所以规格必须是线性缓动才能 1:1 跟手(原来用的减速曲线让页面在手指刚动时就跳出一截);③ 视频页的 SurfaceView 不会跟着页面一起缩放 / 淡出(它在窗口后面"挖洞"显示),退出时视频画面原地不动,只有控制条缩小。
- 现在:层级页面(列表 ← 聊天 ← 设置)手势返回 = 线性 + 整屏跟手滑出,下层页面从 1/4 屏视差滑回,上层页面左边缘有投影;支持从右边缘划;查看器手势返回 = 整页缩小淡出;页面开始退出时对 SurfaceView 用 `PixelCopy` 截图盖在上面再把 SurfaceView 藏起来,视频画面也跟着缩放淡出;手势取消时恢复。
- 注意:测试时曾把"界面动画"设成了"仅淡入淡出",此时返回只有淡入淡出(没有滑动)是预期行为;默认是"滑动 + 视差"。

### 画质增强(实验):实时超分 / 补帧 / SDR 转 HDR
- 设置 → 画质增强(实验),播放时「更多 → 画质增强」也能快速切换。开启任意一项后,视频改由本应用自己的 OpenGL ES 3 渲染器显示(`render/` 包);全关时仍走普通播放,不受影响。
- 结构:ExoPlayer 解码到 SurfaceTexture → 每个源帧:OES→RGBA16F →(超分)→ 帧环形缓冲(+亮度金字塔 +运动估计)→ 每个屏幕刷新(vsync):按 ExoPlayer 给出的上屏时间取相邻两帧 →(插帧)→(SDR→HDR)→ 窗口表面。SurfaceTexture 的时间戳就是 `releaseOutputBuffer` 的上屏时间,帧比上屏时间早到,所以能在两个真实帧之间插值。
- **超分**:直接运行开源的 mpv 用户着色器(自己实现了 `//!HOOK/BIND/SAVE/WIDTH/HEIGHT/WHEN` 的最小运行时,`render/MpvShader.kt`):FSR 1.0(AMD,agyild 的 mpv 移植,MIT,通用、很快)、Anime4K v4(bloc97,MIT,CNN,动漫线条更干净;小 / 中两档)。着色器在 `assets/shaders/`。视频高度超过设定值(默认 900p)不处理;处理耗时连续 2 秒超过帧间隔 90% 时自动停用超分。
- **补帧**:帧混合(便宜,有轻微拖影);运动补偿(实验):亮度三层金字塔块匹配(1/8 层 ±8 全搜索,1/4、1/2 层精修,再做半像素 / 四分之一像素精修),上屏时每个像素在自己与相邻 4 个块的运动向量里挑"前后帧对得最齐"的,匹配不可信的退回混合,差异再大保持最近的帧。补帧时画面整体晚一个源帧间隔(≤50ms)上屏,换取"下一帧"已经到达。屏幕刷新率不够高(< 源帧率的 1.3 倍)时自动不补。模拟器上测得:匀速运动方块的位置残差 RMS 0.21 源像素(帧混合 0.74)。
- **SDR→HDR**:高光扩展的逆色调映射(只抬高光,阴影和中间调不变;大面积亮区少抬,避免整屏刺眼;参考白 203 nit,峰值可选 400–1000 nit)→ BT.709→BT.2020 → PQ,输出到 `EGL_EXT_gl_colorspace_bt2020_pq` 的 10 位窗口表面(窗口切到 HDR 色彩模式),由系统按屏幕能力做色调映射。模拟器没有 HDR 屏,**这一项只通过了编译和着色器链接,没有实机验证**;表面创建失败会自动退回 SDR 并在统计信息里提示。HDR 片源本身不处理。
- 播放页的「显示技术信息」会显示增强渲染的状态:输出帧率、处理耗时、是否因性能停用、HDR 是否生效。
- 开源来源:Anime4K <https://github.com/bloc97/Anime4K>(MIT);FSR 1.0 mpv 移植 <https://gist.github.com/agyild/82219c545228d70c5604f865ce0b0ce5>(MIT);SDR→HDR 的思路参考 <https://github.com/96dot/SDR-to-HDR-Video>(MIT,WebGPU 版);评估过但未采用:RIFE(rife-ncnn-vulkan,神经网络补帧,需要 NDK + Vulkan,手机上实时 1080p 不现实)、Media3 `setVideoEffects`(帧进帧出、不能输出 HDR)。

## 十四、1.1.1:界面转场改成系统风格

- 研究了 Clash Meta for Android(`MetaCubeX/ClashMetaForAndroid`)和 Shizuku(`RikkaApps/Shizuku`):它们都是**多 Activity 应用**,界面之间的前进 / 返回动画**没有自己写**,用的是系统的 Activity 转场(Shizuku 在 manifest 里加了 `android:enableOnBackInvokedCallback="true"` 以启用系统的预测性返回,Clash Meta 直接用默认主题),所以看起来和系统应用一样顺。
- 系统的转场参数(AOSP `activity_open_enter / activity_open_exit / activity_close_enter / activity_close_exit` 与 `fast_out_extra_slow_in`):**只平移 96dp(不是整屏)**,450ms;进入的页面 83ms 淡入(延迟 50ms),离开的页面 83ms 淡出(延迟 35ms);缓动是两段贝塞尔拼成的 Emphasized 曲线 `M0,0 C0.05,0 0.133333,0.06 0.166666,0.4 C0.208333,0.82 0.25,1 1,1` —— 前 1/6 时间先加速,再长长地减速。
- 以前的默认(整屏滑动 + `EmphasizedDecelerate`)生硬的原因:减速曲线一上来就是最大速度,约 70ms 内就走完 90% 的位移,剩下 380ms 几乎看不出变化,视觉上像"闪一下就换了页";而且整屏位移太大。录屏逐帧测过:按钮返回的可见变化只有 4~6 帧(65~100ms),单帧最大跳变占总位移的 70%。
- 现在「界面动画」默认 = **系统风格**:用 AOSP 的参数在 Compose 里复现;手势返回仿系统的跨 Activity 预测性返回(离开的页面缩到 90%、带 28dp 圆角、朝手指一侧偏移、最后淡出,下面的页面带一层随进度变亮的遮罩),全部线性缓动保证跟手。原来的整屏滑动改名「整屏滑动 + 视差(Telegram 式)」,仍可选(带左边缘投影)。
- 排除了一个误判:前进转场里偶尔看到的"一秒卡顿"是测试脚本用 uiautomator 取控件时屏幕静止造成的;不经过 uiautomator 的录屏显示前进转场是连续的 ~28 帧。
- 测试脚本:`testdata/scripts/nav-anim-test.ps1`(所有页面的前进 / 按钮返回 / 手势返回录屏)、`anim-sheet.py`(把转场逐帧拼图)、`anim-curve.py`。

## 十五、1.1.2(仅手机端):每个页面一个 Activity,转场完全交给系统

- 只在 1.1.1 的基础上改了手机端(服务端 / 管理程序仍是 1.1.1)。**这一版按用户要求没有做实机 / 模拟器测试,只保证编译通过**。
- 已经把参考项目克隆到本地:`参考项目\ClashMetaForAndroid`、`参考项目\Shizuku`(浅克隆,已加入 .gitignore)。读源码的结论:两个项目都**没有自己写任何页面转场**,界面都是 Activity,`startActivity()` 进、`finish()` / 系统返回手势出(Shizuku 额外在 manifest 里开了 `android:enableOnBackInvokedCallback="true"` 启用系统的预测性返回),动画全部由系统负责。
- 照着重写:原来的"一个 Activity + Compose NavHost 自己画转场"拆成
  - `MainActivity`:登录页 + 文件夹列表;
  - `ChatActivity`:一个文件夹的聊天 / 网格(里面的"缩略图 ↔ 全屏查看器"仍用共享元素,系统转场做不到);
  - `SettingsActivity`:设置根列表和**每个分类页各自一个实例**(和 Clash Meta 的每个设置页一个 Activity 一样);
  - `SearchActivity`:搜索(查看器同上)。
  进入用 `startActivity`,返回用 `finish()` / 系统返回手势,动画是系统的 Activity 转场 + 系统的跨 Activity 预测性返回(缩小 + 圆角 + 跟手),由系统进程里的窗口动画驱动,不受应用主线程卡顿影响 —— 这是"生硬"的根本解法。
- 为了系统转场不闪:主题的 `windowBackground` 按浅色 / 深色分别设成页面底色(`values/colors.xml`、`values-night/colors.xml`),并在每个 Activity 里按应用的"颜色主题"设置同步窗口背景。
- 细节:二级页面登录失效(401 / 退出登录)时自己 `finish()`,露出下面的登录页;小窗(画中画)回调抽到基类 `TgActivity`,聊天 / 搜索页都支持;Activity 内的 NavHost 只剩"根页面 + 查看器"。
- 可能的副作用:每个 Activity 首次组合比单 Activity 内切换稍慢(窗口背景色先显示),这是多 Activity 方案的固有代价;如果某些页面出现明显空白,请把现象告诉我。

## 二十、服务端 1.2.0:扫描进度稳定显示 + 可只扫某一个盘

- **进度列表不再乱动**:以前服务端用 map 保存各盘的进度,遍历顺序是随机的,管理程序里的盘会来回换位置。现在固定按配置里根目录的顺序排列,而且服务一启动所有盘就都在列表里(位置固定),不是谁开始扫谁才出现。
- **速度稳定**:以前每秒取一次瞬时值再做指数平滑,而且元数据按"每 300 个一批"计数,所以"个/秒"长时间是 0、批完成时突然很大。现在(1)元数据读取改成每处理完一个文件就计数(照片按 30 张一小批给 exiftool);(2)速度 = 最近 10 秒窗口内的计数增量 / 窗口时长;(3)扫描 → 读取元数据切换、新一轮从 0 开始计数时清空窗口,不会出现负数或残留。预计剩余时间也因此更稳。
- **已读取数量不再是 0**:重启后复用旧索引时,进度原来是 0 个文件 / 0 个文件夹;现在启动时就用数据库里已有的数量初始化(后台查询,不拖慢启动),并显示上次完整扫描的时间。元数据进度的"已读"不会超过总数。

## 二十四、手机端 1.6.0:补帧右上角帧率、新增补帧档位与性能优化

- **右上角帧率小字**:开了补帧,画面右上角显示"补帧 24 → 60 fps"(源帧率 → 实际输出帧率,每秒刷新);源帧率已接近屏幕刷新率(例如 60fps 视频在 60Hz 屏上)时显示"补帧待机 60fps"。控制条显示时小字让到顶栏下面。「设置 → 画质增强 → 补帧」里的「右上角显示帧率」可关闭。
- **补帧方式从 2 档增加到 4 档**:帧混合(最省电)/ **运动补偿·轻量**(新)/ 运动补偿(平衡,原来的)/ **运动补偿·高质量**(新)。
  - 轻量:运动场只估到 1/4 分辨率层(格子数是细层的 1/4),只做一轮半像素精修,上屏时每个像素只比较自己所在块的向量 —— 运动估计耗时约为标准档的 1/3,适合 1080p 以上或性能一般的手机;
  - 标准:和以前一样(三层金字塔块匹配 + 半像素 / 四分之一像素精修 + 5 个候选向量);
  - 高质量:再来一轮 1/8 像素精修,上屏时每个像素比较 9 个相邻块的向量,运动边缘更干净,更耗电。
- **性能优化**:
  1. 源帧率已经接近刷新率时**不再做运动估计**(原来每一帧都白算);
  2. 上屏着色器里,两帧几乎一样的**静止区域直接取混合**,省掉每像素 10 次纹理采样(画面里大部分区域是静止背景,这是插帧最大的开销);
  3. 新增**自动降级**(设置「补帧跟不上时自动降级」,默认开):处理耗时连续超过帧间隔时,先停超分,仍然跟不上就依次 高质量 → 标准 → 轻量 → 帧混合,并在"显示技术信息"里标出"已降级"。
- **开源方案调研**(这次没有引入神经网络类方案,原因见后):
  - AMD [FidelityFX Optical Flow / Frame Interpolation](https://gpuopen.com/manuals/fidelityfx_sdk/fidelityfx_sdk-page_techniques_optical-flow/)(FSR 3 的一部分,MIT):亮度金字塔 + 8×8 块匹配求 SAD 最小 + 场景切换检测 + 插帧时遮挡处理。我们的做法和它同一类(金字塔块匹配、场景切换保持原帧),这次借鉴了"按块、分层、可配置质量"的思路,没有直接用它的代码(它是 DX12 / Vulkan 计算着色器,手机上要重写成 OpenGL ES 片元着色器)。
  - [RIFE](https://github.com/nihui/rife-ncnn-vulkan)(神经网络光流,ncnn + Vulkan):质量最好,Android 上已有 GPU 常驻的实现思路([GPU-Resident Frame Interpolation on Android](https://allenkuo.medium.com/gpu-resident-frame-interpolation-on-android-e9558d19cfab)),但要引入 ncnn / Vulkan 原生库、几十 MB 模型,实时 1080p 对手机 GPU 和功耗压力很大,而且我现在没法在真机上验证,所以**暂不集成**,作为以后的可选项(只对 720p 以下做)。
  - 手机厂商的硬件补帧(高通 Adreno Frame Motion Engine、联发科 MEMC)没有给第三方应用的公开接口,用不了。
- 按用户要求没有做运行测试,只保证编译通过。新增的是片元着色器的小改动(候选数、静止早退)和运动估计的档位,默认补帧仍是关闭;补帧着色器如果在个别 GPU 上编译失败,应用会像以前一样自动改回普通播放。

## 二十五、手机端 1.7.0:光流补帧、补帧倍率、保持高刷、硬件支持检测、LSFG-Android 联动、界面风格统一

- **光流补帧(新增补帧方式「光流·OpenCV DIS」)**:集成开源库 OpenCV(官方 Maven 包 `org.opencv:opencv:4.12.0`,Apache-2.0)里的 DIS 稠密光流(Dense Inverse Search,Kroeger 2016)。流程:渲染线程把相邻两帧的 1/4 分辨率亮度读回 → 专用 CPU 线程上用 OpenCV 算每像素运动向量 → 结果回来后上传成纹理,上屏着色器用它做运动补偿(和块匹配共用同一套插帧着色器:逐像素在相邻候选向量里挑最匹配的)。算不过来时(积压 ≥ 2 对)丢弃,该帧对退回帧混合,不会卡画面。自动降级链现在是 光流 → 高质量 → 标准 → 轻量 → 帧混合。光流库在设备上加载失败(架构不支持等)时自动用块匹配最高档。OpenCV 原生库每个架构约 30MB,**发布版只带 arm64-v8a**,调试版另带 x86_64(模拟器)。
- **补帧倍率**:设置「补帧倍率」= 自动(补到屏幕刷新率,原来的行为)/ 2 ~ 5 倍。固定倍率时每个源帧之间只出 N 个画面(N 不超过 刷新率 ÷ 源帧率),其余刷新重复上一个画面,所以 GPU 压力比"自动"小;右上角帧率小字显示的就是实际输出帧率(24fps × 3 = 72)。
- **保持高刷 / 适应省电降帧**:Android 在省电模式或一段时间不触摸后会降低屏幕刷新率,补帧的节奏会乱。现在 (1) 补帧时向系统申请刷新率:窗口 `preferredRefreshRate` + `Surface.setFrameRate`(Android 11+,Android 12+ 允许切换刷新率)+ Android 15+ 的"高帧率类别";固定倍率时申请 源帧率 × 倍率,自动倍率时申请这块屏同分辨率下的最高刷新率;不补帧时释放。(2) 渲染器不再使用启动时读到的刷新率,而是用 Choreographer 实测 vsync 间隔(连续 3 次偏离 25% 以上才切换),系统还是把刷新率降了,插帧间隔和"源帧率已够高就不补"的判断都会跟着变。技术信息里能看到"屏幕 xx Hz"。注意:系统(尤其是 LTPO 屏的厂商策略)最终是否听从申请由系统决定。
- **硬件支持检测**(设置 → 画质增强 → 硬件支持检测):静态能力(OpenGL ES 3、浮点渲染目标、Vulkan 版本、屏幕刷新率 / HDR、CPU / ABI)+ **实测**:在离屏 GL 上下文里用和播放时完全相同的着色器跑一遍 FSR / Anime4K 小 / 中模型(540p → 1080p)、1080p 运动估计(轻量 / 标准 / 高质量)和 OpenCV 光流(480×270),量出每帧耗时,按占 30fps 帧间隔(33ms)的比例判定 良好(≤35%)/ 勉强(≤75%)/ 不支持,并给出推荐的超分和补帧方式,可一键应用。结果存在设置里,下次打开直接显示。检测会占用 GPU 约 5 ~ 15 秒。
- **LSFG-Android**:调研结果(见设置里的说明页「LSFG-Android(外部补帧)」):它是 [FrankBarretta/LSFG-Android](https://github.com/FrankBarretta/LSFG-Android),把 Lossless Scaling 的 lsfg-vk(Vulkan)搬到安卓,用 MediaProjection 屏幕录制 + 悬浮窗叠加生成帧,倍率 2× ~ 8×,要求 Android 10+、Adreno 7xx+;**必须用户自备 Lossless Scaling 的 Lossless.dll**(它在手机上提取着色器后删除 DLL),App 本体许可是"不上架商店、不商用",lsfg-vk 近期改成 CC BY-NC-ND 4.0。所以它**不能作为库嵌进本应用**(DLL 不能分发、是独立的叠加 App)。本应用提供联动页:检测是否已安装、一键打开、项目主页、注意事项(用它时关掉内置补帧、关掉防截屏)。
- **界面风格统一**(检查了登录页、文件夹列表、聊天、搜索、查看器、播放器、设置各页和所有弹窗):
  1. 登录页原来是 Material 默认样式(白底大标题、胶囊按钮),现在和其它页一样:蓝色 TgBar 头部(logo + 标题)、已保存服务器用设置页同样的行 + 分隔线 + 箭头、小节标题同设置页 Header(15sp 强调色)、输入框 / 按钮统一 10dp 圆角、强调色、按钮高 48dp;
  2. 主题里统一了弹窗 / 菜单容器色(日间白、夜间 #212D3B)、圆角(菜单 8dp、弹窗 14dp,原来 Material 默认 28dp)、弹窗标题 18sp(原来 24sp,各处自己写 sp 不一致);
  3. 红 / 绿 / 橙 / 灰这些语义色原来散落在各文件的硬编码里(同一个红色写了 7 处),现在统一成主题的 `danger / ok / warn / neutral`,夜间自动换成更亮的红。
- 按用户要求没有做运行测试,只保证编译通过。需要在真机上留意:光流库能否加载(arm64)、光流算得快不快("显示技术信息"里有"光流 x ms")、系统是否听从刷新率申请、硬件检测的耗时和结果、新登录页的观感。

## 二十六、手机端 1.7.1:修复点开图片 / 视频时闪一下

- 录屏逐帧分析(`testdata\scripts\open-viewer-rec.ps1` + `anim-sheet.py`):点开图片时,聊天页下一帧直接变成全黑,缩略图在黑底上停了一帧,然后全尺寸图才出现 —— 没有过渡。两个原因:

  2. **打开瞬间主线程负担太重**:当前页 + 左右预加载的两页同时解码大图、上传 GPU,转场动画(按时间走)被卡掉了大半。现在转场期间只加载当前页,0.6 秒后再按「预加载页数」设置预加载左右页。
- 模拟器(软件渲染)上录屏确认了占位图生效(点开后缩略图先出现再变清晰,不再是纯黑);模拟器很慢,打开时主线程仍有长时间卡顿,所以转场动画本身的流畅度要在真机上看。

## 三十三、手机端 1.11.0:内置 LSFG(Lossless Scaling 帧生成)

- **前提(用户的声明)**:Lossless.dll 来自用户自己购买的 Lossless Scaling,仅个人使用、不分发。DLL 放在 `参考项目\Lossless.dll`;**它会被打进你自己的 APK,所以请不要把 `dist\` 里的 APK 发给别人**。`参考项目\`、`android\app\src\main\cpp\lsfg\vendor\`、`android\app\src\main\assets\lsfg\` 都在 `.gitignore` 里,DLL 和复制来的源码不会进 git。
- **做法(参考开源项目 [FrankBarretta/LSFG-Android](https://github.com/FrankBarretta/LSFG-Android) 及其子模块 lsfg-vk-android,MIT)**:
  1. `tools\setup-lsfg.ps1`:把 `lsfg-vk-android` 的 framegen / volk / pe-parse / dxbc 和参考项目里提取着色器的代码复制到 `android\app\src\main\cpp\lsfg\vendor\`(必须是纯 ASCII 路径,CMake / Ninja 处理不了中文路径,所以不能直接引用 `参考项目\`),并把 DLL 复制进 assets。运行过之后 Gradle 才会启用 NDK 构建;没运行过就是原来的纯 Kotlin 工程。
  2. 原生库 `liblsfgbridge.so`(`cpp\lsfg\lsfg_bridge.cpp`,CMake 构建,NDK 27 + CMake 3.22.1 已装进 `tools\android-sdk`):从 DLL 提取着色器(DXBC → SPIR-V 48 个 + DLL 里现成的 FP16 / FP32 SPIR-V 各 48 个,优先用 FP32 SPIR-V,绕开 DXBC 翻译器、Mali 也能用),创建 framegen 的 Vulkan 上下文,输入 / 输出图像用 AHardwareBuffer 共享,再把 AHB 绑成 GL 纹理(EGLImage),渲染器直接读写,不经过 CPU。
  3. 渲染器(`VideoRenderer`):新补帧方式「LSFG 帧生成」。每个真实帧渲染进输入 AHB(槽 = 帧号 % 2)→ `glFinish` → `presentContext` + `waitIdle` → 把生成的 k 张中间帧拷进纹理池挂在这一帧上;上屏时按时间位置挑最近的那张(第 0 张是前一帧本身)。倍率 = 「补帧倍率」(2 ~ 8,自动 = 补到这块屏的最高刷新率,不超过屏幕能显示的);k 变化 / 画面尺寸变化时重建会话。
  4. 设置:补帧方式里选「LSFG 帧生成」;「补帧倍率」扩到 2 ~ 8;「LSFG 光流精度」(25% / 50% / 75% / 100%,1080p 以上建议 ≤ 50%);「LSFG 性能模式」(3.1P)。播放中「更多 → 画质增强」里也能选。「设置 → 画质增强 → LSFG 帧生成」页显示 原生库 / DLL / 着色器缓存 状态,可以手动提取 / 重新提取着色器。硬件检测里也新增了内置 LSFG 的前置条件。
  5. 失败回退:着色器还没提取完(第一次约几秒)、原生库没加载、Vulkan / AHB 不支持、启动失败 2 次或设备丢失,本次播放自动改用光流(再不行块匹配 → 帧混合);跟不上时「补帧跟不上时自动降级」也会把它降下去。
- **模拟器上验证了**:原生库在 x86_64 模拟器上加载成功;用你的 Lossless.dll 提取着色器成功(48 个 DXBC 翻译 + 48 FP16 + 48 FP32)。**没有验证**:framegen 的 Vulkan 管线、AHB ↔ GL 互通和实际生成效果 —— 模拟器没有真实 GPU,要在真机(Adreno 7xx+ 最稳,天玑 / Mali 看驱动)上测。如果真机上选了 LSFG 却回退到光流,到「设置 → 日志与诊断」里找 `lsfg` / `lsfg-bridge` 的日志(原因会写在里面),发给我。
- 构建:`tools\build-android.ps1` 现在会先 `subst L:` 把项目根目录映射成盘符再构建(原生构建需要 ASCII 路径)。发布版只带 arm64-v8a(OpenCV + 原生库),调试版另带 x86_64。

## 三十四、手机端 1.11.1:LSFG 改成异步生成;右上角小字能看出到底在用什么、为什么回退

- **"补帧待机"其实是显示 bug**:LSFG 上屏时直接显示生成帧(走"单帧"路径),而右上角小字用"是不是单帧路径"判断待机,所以 LSFG 正在工作也显示"补帧待机"。现在小字会写清楚在用哪种方式:`补帧 24 → 96 fps · LSFG ×4`;LSFG 没启用时写原因:`· LSFG 未启用:正在提取着色器 / 启动失败原因 / 已降级`。
- **画面帧率反而更低的原因**:以前 `presentContext + waitIdle` 同步跑在渲染线程上,生成一次要几十毫秒,这段时间渲染线程(同时负责每次屏幕刷新的上屏)被堵住了,上屏掉帧。现在改成:渲染线程只负责把这一帧渲染进输入 AHB(含 `glFinish`),然后交给专用线程做 `presentContext + waitIdle`,做完回到渲染线程把生成的 k 张中间帧拷进纹理池挂到这一帧上。渲染线程不再等 Vulkan。
  - worker 还在生成时来的新帧不处理(输入 AHB 还被它读着,不能覆盖),这些帧没有生成帧,上屏时退回帧混合;生成帧只在"前一个处理的帧就是紧挨着的上一帧"时才有效,否则丢弃(避免时间对不上)。
  - **来不及自动降级**:最近 24 个帧里超过一半被丢(生成速度跟不上源帧率),且开着「补帧跟不上时自动降级」,就降到光流,日志里写明(`lsfg`)。LSFG 现在也受耗时预算的自动降级管理(以前只管块匹配 / 光流)。
  - 释放时会等 worker 做完再释放原生资源。
- 这个 GPU 上 LSFG 如果还是太慢:把「LSFG 光流精度」调到 25%、开「LSFG 性能模式」、降低「补帧倍率」。
- 按用户要求没有做运行测试。

## 三十五、手机端 1.11.2:LSFG "一会卡一会流畅"——按覆盖率自适应、降低拷贝开销、加大延迟余量

- **现象的原因**:LSFG 的生成速度偶尔跟不上源帧率 → 有的帧区间有生成帧(流畅)、有的没有(退回帧混合,看起来像源帧率的卡顿),两种交替就是"一会卡一会流畅"。另外生成有几十毫秒延迟:一个区间的前半段生成帧还没回来、后半段才有,也会抖。
- **改动**:
  1. **覆盖率**:统计每个上屏的帧区间"有没有生成帧",右上角小字显示 `LSFG ×4 精度50% 覆盖93%`。覆盖率 100% = 全程流畅;低了就是在交替卡顿。
  2. **按覆盖率自适应**(设置「补帧跟不上时自动降级」开着时):每 24 个区间评估一次,低于 85% 就先把光流精度降一档(100 → 75 → 50 → 35 → 25%,重建会话,日志里写明),已经是最低档还不行才降级到光流。设置里的「LSFG 光流精度」是上限,自动调整只会往下调。
  3. **更大的延迟余量**:LSFG 工作时画面比声音再晚一点(最多 80ms,原来最多 50ms),让生成帧在对应区间开始前就绪,避免区间中途才出现生成帧。
  4. **拷贝开销**:每个源帧要把 k 张生成帧从 AHB 纹理拷进纹理池,原来用 RGBA16F(每张 16MB@1080p),现在改用 RGBA8 的池,带宽降到 1/4。
- 仍然跟不上:把「LSFG 光流精度」直接设成 25%、开「LSFG 性能模式」、降低「补帧倍率」;或者这台 GPU 实在跑不动 LSFG,改用「光流·OpenCV DIS」。
- 按用户要求没有做运行测试。

## 三十六、手机端 1.11.3:修复 LSFG "覆盖率 90% 以上还是时卡时流畅"——相位累加器(锁相环)

- **真正的原因是上屏节奏,不是生成帧缺失**:LSFG 每个真实帧之间有 n 个"相位"(真实帧 + n−1 张生成帧),以前每个 vsync 用 `floor(t × n)` 按当前时间取相位。当 源帧率 × n 正好等于屏幕刷新率(24fps × 5 = 120Hz、30fps × 4 = 120Hz 这类整数倍,高刷屏上最常见)时,每个 vsync 的采样点正好落在相位边界附近 —— 源时钟和屏幕时钟只要有千分之一的漂移、vsync 有 1~2ms 的抖动,同一个相位就会时而被显示两次、时而被跳过。这种漂移是慢的,所以表现就是"几秒流畅、几秒卡顿"交替,而且和覆盖率无关。
- **修法**:改用相位累加器(软件锁相环)。每个 vsync 前进 `n × 源帧率 / 刷新率` 个相位(整数倍时恰好 1 个),再朝真实时间慢慢靠拢,真实时间和累加器之间 ±0.3 个相位以内不修正;偏差更大才慢慢拉回,偏差超过 2.5 个相位直接重置。这样整数倍时每个 vsync 恰好前进一个相位,不重复也不跳过;非整数倍(24 → 60Hz 之类)时是固定的重复规律。相位 → 纹理的对应是按"真实帧 id × n + 第几张"在帧环里查的,生成帧不全的区间退回按时间取。
- 其它可能的因素(这版没有解决):GPU 的调频(负载一阵一阵时 GPU 频率忽高忽低,生成就时快时慢)、发热降频。右上角小字里的覆盖率和精度仍然会显示。
- 按用户要求没有做运行测试。

## 三十七、手机端 1.11.4:补帧详细日志

设置 → 画质增强 → 补帧里的「补帧详细日志」(默认开)。补帧工作时每 2 秒往日志写 4 行汇总(标签 `frc`),异常时立即写一行事件(以 `! ` 开头,10 秒内最多 40 条)。日志在「设置 → 日志与诊断 → 分享日志文件」里导出。

汇总行里的数字大多是 `平均/最小/最大`(毫秒):

1. `===== 2.0s 配置=… 屏幕 …Hz(间隔 …ms,最高 …Hz) | 源 …fps 输出 …fps | 热状态=… | ingest 平均 …ms`:配置、实际使用的方式(被降级会显示)、倍率、LSFG 每帧生成数 k、光流精度、屏幕实测刷新率、源帧率、系统热状态(0 无 … 3 严重)。

4. (LSFG)`相位 正常X 重复X 跳过X 倒退X | 区间无生成帧X 相位查不到X | 写输入ms | 生成(worker)ms 渲染线程收尾ms | 生成帧年龄ms 晚于区间开始X次 | 忙丢帧X 生成失败X 覆盖=…%`:**相位重复 / 跳过 = 肉眼看到的卡顿**;生成(worker)耗时和源帧间隔比;生成帧晚于对应区间开始上屏的次数;忙丢帧。

## 三十八、手机端 1.11.5:根据日志修复 LSFG 会话反复重建 + 屏幕刷新率来回切

分析 `bugs\localbrowse-log-20261006-093610.zip`(OPPO OPD2515,**Adreno 829,Vulkan 1.4**,1080p 30fps 视频,LSFG ×5、精度 50%、3.1P)得到的结论:

- **LSFG 本身没问题**:worker 生成耗时稳定 **23 ms**(22.7 ~ 25),远小于 30fps 的帧间隔 33 ms;没有生成失败;热状态 0。没出问题的窗口里(例如 09:35:36 ~ 09:35:44):源帧间隔 33.3/33.3/33.3、vsync 一个不丢、欠载 0、覆盖率 100%、相位恰好每 vsync 前进 2 个(屏幕 60Hz 时 4 个相位里隔一个取)—— 很稳。
- **卡顿的两个来源**:
  1. **LSFG 会话每隔一两秒重建一次**(日志里 `会话已建立 每帧生成 3 张 / 4 张` 交替出现):每帧生成数 k 以前用 `floor(屏幕最高刷新率 144 / 瞬时源帧率 + 0.15)` 算,源帧率估计值在 28.8 ~ 30 之间抖,商在 4.8 ~ 5.0 之间,k 就在 3 和 4 之间跳,每跳一次就销毁 / 重建会话(分配缓冲、建 Vulkan 管线),渲染线程被卡 **0.4 ~ 0.5 秒**(日志里 `源帧间隔 最大 425 ~ 533ms`、`ingest CPU 最大 460 ~ 544ms`、`swap间隔 最大 470 ~ 674ms`),这一秒里源帧率只有 9 ~ 20fps、一堆区间没有生成帧。
  2. **屏幕在 120Hz / 60Hz 之间来回切**(`屏幕刷新间隔变化 120Hz → 60Hz → 120Hz`):每次切的时候 vsync 异常、swap 阻塞。原因是我们向系统申请的刷新率在 `144 Hz / 142 Hz / 141 Hz` 之间不停改(固定倍率时申请 `源帧率 × 倍率`,源帧率估计值一抖申请值就变),每次申请变了系统都重新选刷新率。
- **修复**:
  1. **每帧生成数 k 定下来就不再变**:固定倍率 m → k = m − 1(不再按屏幕上限砍);自动 → 补到 120Hz(最高刷新率不到 115 就补到 60Hz)附近,按标准化的源帧率(23.976 / 24 / 25 / 29.97 / 30 / 50 / 59.94 / 60…,3% 以内算同一档)算一次;只有倍率设置变了、或源帧率变化超过 30% 才重算。日志里会有一条 `LSFG 每帧生成数定为 k`。
  2. **刷新率申请固定且不再乱改**:补帧时只申请一个固定的刷新率(同分辨率下 ≤ 120Hz 里最高的:120 是 24 / 30 / 60 / 120 的整数倍,上屏节奏均匀;144 不是 30 / 60 的整数倍,30fps 补到 144 是 4.8 倍,还更费电),并且同时设窗口的 `preferredDisplayModeId`(比 `preferredRefreshRate` 更"硬")。日志里会列出这块屏的所有显示模式(`所有模式 …`)。
- **没有解决 / 需要继续看**:日志里屏幕有一半时间被系统压在 60Hz(ColorOS 的省电 / 久不触摸降刷新率策略),这时 4 个相位只显示隔一个,输出是均匀的 60fps(比不补帧的 30fps 好,但没有发挥 120Hz)。这版把目标刷新率和显示模式固定后,看下一份日志里 `屏幕 xx Hz` 是不是稳在 120。
- 按用户要求没有做运行测试。

## 三十九、手机端 1.11.6:根据第二份日志——生成线程排队不丢帧、LSFG 降为低优先级、生成数按刷新率封顶

  3. **生成数按刷新率封顶**:倍率不超过 `目标刷新率 / 标准化源帧率`(30fps 在 120Hz 上封顶 ×4,k = 3,生成耗时回到 ~23ms)。输入都是稳定的(标准化源帧率 + 固定的目标刷新率 + 只算一次),不会再引发重建。选 ×5 而屏幕 120Hz 时实际是 ×4,日志里有 `LSFG 每帧生成数定为 k`。
- 想要更满的生成:30fps 的片源 ×4 刚好 120fps,是 120Hz 屏的最佳点;24fps 的片源 ×5 正好 120。如果你的屏幕能稳定 144Hz,可以继续告诉我,再把目标刷新率改回 144。

## 四十九、手机端 2.2.0:天玑 / Mali 上补帧"性能跟不上"——FP16 着色器 + 降输入分辨率

分析 `bugs\localbrowse-log-20261006-152137.zip`(vivo V2502A,**Mali-G1-Ultra MC12**,Vulkan 1.3,`shaderFloat16=1`,1080p 30fps):

- 同样 1080p、光流精度 50%:**k = 3 时 worker 要 60 ~ 65ms(屏幕 120Hz)/ 113 ~ 119ms(屏幕被系统压到 60Hz)**,k = 1 要 28 ~ 53ms;骁龙 8 Elite(Adreno 829)上 k = 3 只要 25ms。帧间隔 33ms,覆盖率 0%,降光流精度也没用(日志里 50% 已经到不了更低有效档),连续 4 次不达标后停用补帧,右上角提示"性能跟不上"。
- 原因:
  1. **一直在用 FP32 着色器**。当初为了兼容性(绕开 DXBC 翻译、不需要 vulkanMemoryModel)默认选了 DLL 里现成的 FP32 SPIR-V;Mali 的半精度算力是单精度的两倍(寄存器占用也少一半),官方 FP16 着色器在 Mali / 天玑上差距最大。这台设备明明支持 `shaderFloat16`,framegen 的设备创建也已经会按支持情况打开对应特性,只是着色器没选 FP16。
  2. **只有光流精度这一维可降**:帧生成里的 warp / 融合 / 生成 pass 都是全分辨率的,光流精度压低省不了多少。
  3. 系统在 60Hz / 120Hz 之间来回切屏(日志里 `屏幕刷新间隔变化` 反复出现,甚至掉到 24Hz),屏幕 60Hz 时 GPU 频率明显更低(同样负载 worker 耗时翻倍),这个我们控制不了。
- **修复**:
  1. **着色器优先 FP16**(`nativeStart` 新增 `preferFp16`):FP16 → FP32 → DXBC;FP16 初始化失败、或创建管线时被驱动拒绝,原生层自动退回 FP32 重来。设置 → 画质增强 新增「LSFG 强制 FP32 着色器」开关(默认关),FP16 在某些驱动上画面异常时打开。日志里 `会话已建立` 和每 2 秒汇总都会写 `着色器 FP16 / FP32`。
  2. **自动降级加了"输入分辨率"一维**:档位表 = 光流精度逐档降到 25%,再把整个帧生成的输入分辨率降到 75%、50%(像素数 56% / 25%,生成的中间帧略糊,上屏时线性插值放大,真实帧仍是原分辨率);沿用"降光流精度没有变快就退回、以后只降输入分辨率"的判断。右上角小字和日志里会写 `输入 xx%`。
- 预期:FP16 如果在这块 Mali 上跑起来,worker 耗时能明显下降;还不够就会自动降到 75% / 50% 输入分辨率。想要最稳,可以用「低功耗」档(只生成 1 张)。

## 五十、手机端 2.2.1:天玑 / Mali 上的补帧——FP16 实测、切屏顿挫、倍数自动减半

分析 `bugs\localbrowse-log-20261006-153349.zip`(2.2.0,vivo V2502A,Mali-G1-Ultra,1080p 30fps):

- **FP16 有效**(`着色器=FP16`):低功耗(k = 1)worker 从 28 ~ 53ms 降到 **20 ~ 21ms**,覆盖率 100%,相位 `正常 121 / 重复 1`(60Hz 屏)、`正常 120 / 重复 122`(120Hz 屏,每个相位显示 2 个 vsync,符合预期)——稳态节奏是干净的。标准(k = 3)在 120Hz 屏第一个窗口 24ms,但之后 28 ~ 59ms 上下波动(屏幕被系统压到 60Hz 时更慢),贴着 / 超过 33ms 帧间隔,覆盖率 25 ~ 70%,4 次不达标后停用。
- **画面抖动的最可能原因:系统在 60Hz / 120Hz 之间反复切屏**(日志里每隔几秒一次 `屏幕刷新间隔变化`,我们申请 60Hz 时系统也会切回 120Hz)。相位累加器以前每个 vsync 前进 `n × 源帧率 / 测出的刷新率`,而"测出的刷新率"要连续 3 次偏离才更新,切换后的前几帧相位前进量差一倍(快 2 倍或慢一半),随后追赶,切换点上就是一次顿挫。
- **改动**:
  1. 相位按**这个 vsync 实际过去的时间**前进(`n × 源帧率 × 实际间隔`),不再依赖测出的刷新率;刷新率变化判定从连续 3 次改成 2 次;
  2. 相位校正又松又慢:死区 ±0.6 个相位、每次补 3%(以前 ±0.3 / 10%),帧时间戳本身有几毫秒抖动(切屏时更大),追得太紧会把抖动搬到画面上;
  3. 自动降级档位加了"**生成倍数减半**"(×4 → ×2,60 / 120Hz 都是整数倍,节奏照样均匀):光流精度档 → 倍数减半 → 输入分辨率 75% → 50%;生成耗时比帧间隔长 30% 以上时直接跳到"倍数减半",不再一档档试光流精度(每次重建会话要 1 秒多);已经是 ×2 的跳过无效档位。这台 Mali 上标准模式预期会自动落到 ×2(k = 1,约 20ms,输出 60fps)而不是直接停用。
- **查了驱动 / 管线**:
  - 着色器就是 Lossless.dll 里的官方 SPIR-V(FP16 / FP32),我们不能改;Arm 的《GPU Best Practices》建议 64 线程 / 工作组、半精度要向量化(`f16vec2`)—— 官方 FP16 着色器正好是这个方向,这也解释了为什么 FP16 在 Mali 上差距这么大。
  - framegen 每帧提交 1 + k 次 `vkQueueSubmit`(金字塔 1 次,每张生成帧 1 次,用二值信号量串联),每帧还新建命令缓冲 / 信号量 / 栅栏。把 k 次提交合成 1 次理论上能省一点提交开销,但日志里 k = 1 → k = 3 只多 4 ~ 16ms(每张生成帧的实际计算量),固定部分(金字塔 + alpha + beta)才是大头,而且改它没法在真机上验证、出错会花屏 / 挂起,所以没动。
  - 队列已经是 LOW 全局优先级、GL 上下文 HIGH(OPPO / 骁龙上验证过);天玑 / Mali 上 LOW 优先级会不会让生成被饿着,目前日志看不出来(k = 1 稳定在 20ms),先不动。
  - 参考资料:Arm GPU Best Practices(工作组大小、FP16 向量化)、LSFG-Android 的 Mali 支持讨论(issue #12,主要是叠加层截屏反馈问题和 Mali-G77 上的 Vulkan 1.1 兼容 / L2 缓存刷新 / AFRC 图像布局,和我们这条"应用内渲染 + AHB 共享"的路径不同,没有直接可用的改动)。
- **没解决 / 需要你验证**:低功耗模式"抖动非常严重"在日志里稳态节奏是干净的,切屏点的顿挫是我能确认的一个原因;如果这版还是抖,请(1)打开 设置 → 画质增强 →「LSFG 强制 FP32 着色器」对比一下是不是 FP16 在 Mali 上的生成帧有问题(形变 / 亮度闪烁),(2)再发一份日志,我看 `相位` 和 `选帧` 行。

## 五十三、服务端 / 桌面 1.3.1:打开日志文件夹无反应、缓存占用乱跳、扫描卡住

用户反馈(管理程序截图:E: 盘"扫描中 · 0 文件/秒 · 接着上次中断的扫描继续",其它盘已完成):

1. **点"打开日志文件夹"没有反应**:前端走 Tauri opener 插件的 `openPath`,而 `opener:allow-open-path` 需要在权限里逐个声明允许的路径范围,`C:\MediaHub\data\logs` 不在范围里,被拒绝;前端没处理这个异常,表现就是点了没反应。改成自己的 Rust 命令 `open_path`(`explorer.exe` 打开文件夹 / 用默认程序打开文件;目录不存在先建出来),前端失败时弹出错误提示。"导出日志包"后打开所在文件夹、崩溃报告的"打开"都走它。
2. **各盘缓存占用盘符上下乱跳**:`/admin/status` 的 `cache` 列表来自 `Cache.All()` 遍历 Go 的 map,顺序每次都不一样。现在按根目录 id 排序,位置固定。
3. **扫描卡住不扫描**(按代码推断三个原因,都处理了):
   - **扫描失败后状态一直停在"扫描中"**:`ScanRoot` / `Enrich` 出错(例如多个盘同时写 SQLite 时某个事务等锁超过 10 秒返回"database is locked")时只写了一条日志、函数直接返回,进度状态还是 `scanning`,而那个盘的循环要等下一个定时周期(或手动点重扫,但按钮在"扫描中"是灰的)才再动 —— 看起来就是卡住。现在失败时状态改成 `error` 并写明原因,**自动重试**(30 秒、60 秒…最长 5 分钟,扫描可续扫不会从头来);"出错"状态下"只扫这个盘"按钮可用(以前 `state != idle` 一律当作忙,按钮灰着)。
   - **SQLite 忙等待时限 10 秒太短**:6 个盘并发扫描,某个盘的"对话计数整理"(Finalize)是整库相关子查询,持锁时间长,别的盘的写事务等不到就失败。`busy_timeout` 提到 60 秒。

## 六十二、手机端 2.13.0:强制屏幕保持 120 Hz 及以上

- `render/HighRefresh.kt`:`targetMode` 取当前分辨率下刷新率 ≥ 119.5 Hz 的显示模式里最高的(没有就不强制);`apply(activity, on)` 把窗口的 `preferredDisplayModeId` 和 `preferredRefreshRate` 设成它(比只设 `preferredRefreshRate` 更"硬",系统的智能刷新率更不容易降下去),Android 15+ 再把根 View 的 `requestedFrameRate` 设成"高帧率类别"(VRR 屏幕画面静止时也不降到 60 / 30)。关掉开关恢复 0 / `NO_PREFERENCE`。
- `TgActivity`(所有页面的基类)在 `onCreate`、`onResume`、设置变化、`DisplayListener.onDisplayChanged` 时重新套用,因为系统(省电 / 画中画 / 多窗口 / 接外接屏)可能把请求清掉;`onDestroy` 取消监听。设置 `forceHighRefresh` 默认开启,在 设置 → 外观 → 屏幕。
- `EnhancedVideoView.applyRateHint`:开着强制时,补帧申请的刷新率(例如低功耗档的 60 Hz)取不低于强制档位(60 帧内容在 120 Hz 上是整数倍,画面照样均匀);释放(0)时退回强制的模式而不是交给系统。
- 限制:应用只能"请求",系统省电模式、过热降频、用户在系统设置里手动锁了刷新率时仍可能覆盖,应用管不了。日志 `refresh` 标签会记录选了哪个模式。

## 六十三、手机端 2.14.0 / 服务端 1.9.0:更新用镜像与备用 DNS

- 服务端 `internal/update/net.go`:`resolve` 顺序为 缓存(10 分钟)→ DoH(`dns.alidns.com` 223.5.5.5、`doh.pub` 1.12.12.12、`cloudflare-dns.com` 1.1.1.1、`dns.google` 8.8.8.8,用 JSON API `?name=&type=A`,DoH 服务器本身用固定 IP 连接以避免鸡生蛋问题)→ 系统 DNS → 过期缓存。`newHTTPClient` 的 DialContext 用上面的解析结果逐个 IP 尝试。
