# 安卓端实用功能规划与开源参考

调研日期：2026-10-25。代码基线：`c697d1c`，LocalBrowse 4.0.2 / MediaHub 3.3.3。

## 1. 建议先做什么

最值得增加的是：收藏与自定义合集、继续观看与历史、批量操作、可靠的离线下载、组合搜索。它们分别解决“喜欢的找不到、上次看的找不到、整理太费事、离线不能用、大库筛选困难”。

现有播放器与画质增强已经很丰富，下一轮优先把媒体浏览变成可积累的个人媒体库。界面继续使用现有 Telegram 风格，保留“文件夹 / 随机 / 设置”三个底部标签。

这份方案包含 14 个项目的官方仓库/README 对照，以及当前代码核查。外部项目功能是资料确认，推荐优先级、交互和工期是针对本项目的判断；未安装评测全部外部应用，也未完成其源码级实现审计。分支 README 可能包含尚未进入正式版的功能，不作为某个已发布版本的保证。

## 2. 当前已经有的能力

| 方向 | 当前代码证据 | 本次规划如何补充 |
|---|---|---|
| 浏览 | ChatScreen：聊天流、网格、瀑布流、排序、类型过滤、日期定位；SearchScreen：文件名搜索 | 新增跨条件检索、收藏入口，不重复开发网格/排序 |
| 续播 | Settings.kt 的 PlaybackStore；Api.kt 的单媒体进度读写；服务端 user_playback | 增加可浏览的历史列表、已看状态和继续观看入口，不把“已有续播”重新立项 |
| 保存 | SaveToPhone.kt 已能保存单个原文件到手机相册 | 增加持久任务、断点恢复、批量下载及离线入口；“保存到相册”和“应用内离线”分别呈现 |
| 视频缓存 | VideoCache.kt：直放/兼容版 LRU 缓存、下一项开头预缓存 | 缓存会淘汰，也不保证文件完整，不能直接标成“已离线” |
| 播放 | 手势、倍速、A-B 循环、自动下一项、PiP、音轨/内嵌字幕、字幕样式、解码/转码回退 | 新增外置字幕、字幕延迟、书签/章节、任务队列；不重做播放器引擎 |
| 隐私 | screenSecure；已有服务器令牌和 TLS 信任机制 | 可增加应用解锁和脱敏分享；不能宣称已有完整加密保险箱 |
| 本地模式 | LocalMedia.kt 从 MediaStore 读取图片/视频，通过 LocalInterceptor 复用界面 | 增加明确授权目录的 SAF 入口，服务端新能力在本地提供适配或禁用说明 |

参考源码均位于 `android/app/src/main/java/com/localtg/`，服务端状态相关代码位于 `server/internal/api/userstate.go` 和 `server/internal/store/schema.go`。

早期总览中的“只在局域网、不分发”等设定已与当前 HTTPS、多服务器和公开 release 状态不同，本方案以当前代码为准。

## 4. 第一批：收藏、继续观看、批量操作

### A. 收藏与自定义合集——最高优先级

**使用场景：**随机刷到喜欢的视频可以一键保存；不同文件夹的内容放入“稍后看”“旅行参考”等合集，无需移动 NAS 文件。

- 查看器增加收藏按钮，媒体长按菜单提供“加入合集”。
- 合集是引用，同一媒体可加入多个合集；删除合集不删除文件。
- 文件夹页顶部增加折叠的“快捷入口”：收藏、继续观看、合集、下载。低频项目可隐藏，不增加底部标签。
- 首期按服务器和账号保存收藏/合集，同一页面可查看来源；跨服务器混合合集后置，避免早期同步复杂化。
- 无网络时能查看缓存的标题/封面并修改收藏，变更进同步队列；未离线的媒体明确显示需要连接。

**实现：**新增用户收藏、合集及成员关系；客户端持久存储待同步变更。用户私有状态不能放进共享 media 行。先完成下文的稳定媒体身份，再接入服务端同步。

**验收：**重复点击不会生成重复条目；改名/重扫后关联不丢；存储优化替换后仍在合集；删除合集不触碰原文件；A 服务器的收藏不会混到 B 的同名文件。

参考：[Immich 的收藏/相册](https://github.com/immich-app/immich/blob/main/README.md)、[Mihon 的分类](https://github.com/mihonapp/mihon/blob/main/README.md)。

### B. 继续观看、最近浏览、已看状态

**使用场景：**不用记住在哪个文件夹，直接回到昨天看到一半的视频或刚浏览的图片。

- 文件夹页展示可折叠的“继续观看”横排，最多 8 项；完整历史在快捷入口中分页打开。
- 视频卡片显示进度和剩余时间；支持“从头播放”“标记已看/未看”“从历史移除”。
- 历史分视频与图片，图片默认只记最近打开项目，避免每次滑过缩略图都写记录。
- “看完”与“进度为 0”分别记录；不能把手动回到开头误判为已经看完。
- 自动已看阈值建议初始为 95%，作为可调整的产品规则；极短视频和片尾长的视频允许手动覆盖。
- 暂停记录只影响后续新增记录；清空历史要明确是否同步清除服务端记录。

**实现：**复用现有进度读写，新增历史列表查询、显式观看状态及最近访问时间。当前只有单媒体进度接口，不是只加一块 UI 就能完成。

**验收：**切换设备不把旧进度覆盖新进度；用户“从头播放”可正常同步；旧版服务器仍能按现有方式续播；无权限或文件消失时能移除失效记录。

参考：[mpvKt 的历史](https://github.com/abdallahmehiz/mpvKt/blob/main/README.md)、[Auxio 的状态持久化](https://github.com/OxygenCobalt/Auxio/blob/dev/README.md)。

### C. 长按多选与批量操作

- 长按网格/聊天流中的媒体进入选择模式，顶栏显示已选数量；返回键先退出选择。
- 首期支持批量收藏、加入合集、加入下载队列；多选状态在网格/瀑布流切换时保留。
- “全选当前已加载”与“选择全部搜索结果”分别命名，不能把前 60 条当作全库。
- 批量请求返回成功、失败、跳过明细，可只重试失败项目。任务进行时显示进度，允许取消未开始项目。
- NAS 原文件移动/删除先不放进首期菜单；本地删除如后续加入，应走系统确认和可恢复流程。

**验收：**跨分页选择不重复；刷新/排序不把选中状态移到别的文件；取消下载不删除源文件；所有批量数量可以对账。

参考：[Seal 的批量下载与管理](https://github.com/JunkFood02/Seal/blob/main/README.md)、[Material Files 的操作反馈](https://github.com/zhanghai/MaterialFiles/blob/master/README.md)。

## 5. 第二批：离线下载与组合搜索

### D. 真正的下载中心

这是价值很高、也最不适合匆忙拼接的功能，建议单独一个迭代。

**用户可见行为：**

- 菜单分别提供“离线保存”和“导出到手机相册”。前者由应用管理，后者沿用系统相册可见的导出行为。
- 下载中心展示排队、下载中、已暂停、已完成、失败及明确原因；支持暂停/继续、取消和批量重试。
- 默认仅在不计量网络下载，首次加入显示估计体积与可用空间；提供限速、并发上限与磁盘配额。
- 断网、重启和进程被杀后恢复任务；源文件变化时丢弃不匹配的分段，不能拼接不同版本内容。
- 离线页保存必要标题、来源、封面和字幕引用，断网时能独立进入并播放，不依赖在线列表。
- 删除离线副本只删本机文件；用户主动下载的完整媒体不受播放 LRU 缓存清理影响。

**分两步实现：**第一步只下载原文件和已完成的兼容版本。暂不把临时 HLS 目录当离线成品。第二步再评估“节省空间的离线版本”，复用服务端可控转码任务，并和正在播放、存储优化队列统一调度。

**技术取舍：**视频优先评估 Media3 DownloadService/DownloadManager 与现有认证数据源适配；图片走持久化的文件任务。两者共用任务列表、配额和取消语义，避免引入多个互不协调的下载引擎。后台执行遵守目标 Android 版本限制，不承诺被系统强制停止后仍持续下载。[Android 官方下载架构](https://developer.android.com/media/media3/exoplayer/downloading-media)明确区分了在线缓存和离线下载，也提供持久状态与后台服务方案。

**验收：**断点恢复；鉴权失效；空间不足；源文件变化；切换服务器；断网重启后的完整离线播放；删除应用内副本不影响已导出到系统相册的文件。

参考：[Findroid](https://github.com/jarnedemeulemeester/findroid/blob/main/README.md) 的离线功能与 [Seal](https://github.com/JunkFood02/Seal/blob/main/README.md) 的任务管理。具体断点/调度实现以上述官方接口与本项目原型验证为准，不能只凭外部项目功能表认定已经解决。

### E. 组合搜索、保存筛选条件

**使用场景：**查“F 盘、某文件夹、今年新增、超过 20 分钟、还没看过的视频”，而不是只能记住文件名。

- 搜索框下方增加可折叠筛选条件：来源/盘符、文件夹、类型、日期范围、时长、大小、收藏/已看。
- 时间字段明确区分拍摄时间、修改时间、加入库时间；现有库没有可靠加入时间时不假造，需新增字段并说明旧媒体值未知。
- 活跃筛选以可移除的小标签展示，支持一键清空。
- 可保存为“智能合集”，例如“未看过的长视频”；保存的是条件，不是复制文件或整套全库结果。
- 本地 MediaStore 模式只显示能正确支持的条件；不能静默忽略筛选后返回更宽的结果。

**实现：**扩展服务端搜索参数、稳定游标和总数语义；按实际执行计划补索引。与收藏/观看状态联查，客户端不下载全库后自行过滤。

**验收：**组合条件分页无重复/漏项；数量与全选语义一致；短中文关键词有明确匹配规则；拍摄时间缺失的内容行为明确。

参考：[Aves 的元数据导航](https://github.com/deckerst/aves/blob/develop/README.md)、[Immich 的多维搜索](https://github.com/immich-app/immich/blob/main/README.md)。本轮先做确定性的元数据搜索，不把人脸/CLIP 搜索算作低成本扩展。

| 更实用的随机浏览 | 选收藏/指定合集、排除已看、最近不重复、记录本轮访问 | 依赖用户状态；不为任意筛选预热整套序列 | P1，放在收藏/历史之后 |

| 投屏 | 先选一种协议做设备发现、播放、暂停、断开的小原型 | 接收端鉴权、TLS、字幕和编码兼容；成本高 | P2，先验证再承诺 |

| 手机照片自动备份、AI 人脸/语义搜索 | 另立需求和资源评估 | 涉及上传、去重、模型、数据恢复和新增后台负载 | 暂缓 |

平台实现参考：[BiometricPrompt](https://developer.android.com/identity/sign-in/biometric-auth)、[MediaSessionService](https://developer.android.com/media/media3/session/background-playback)。不把 UI 模拟通过当作后台播放、文件权限或生物识别能力已验证。

### 字幕和投屏的边界

字幕首期不做在线字幕站聚合；先保证用户自己选字幕、调延迟和记住关联可靠。投屏不能简单把带长期令牌的现有视频 URL 交给电视，应另行设计范围受限、短期有效的播放授权。电视必须实际能访问服务器，手机能连通不代表电视能连通；手机端超分/补帧也不会自动出现在电视上。

## 7. 共同的技术前置工作

### 稳定媒体身份与版本

当前索引媒体 ID 与文件身份有关，压缩替换会移走原媒体并重扫。新增长期用户状态前，需要引入或明确可跨替换保持的逻辑媒体标识，例如服务端分配 `asset_uid`：

- 正常改名、移动及已知的压缩替换过程显式保留关联。
- `revision`/指纹表示文件内容版本，供下载恢复、封面和字幕关联判断是否失效。
- 不按同名文件自动合并身份；磁盘丢失、根目录移除和真实删除分别处理。
- 没有确证映射的旧记录保留为失效项，允许用户移除；不能错误附着到另一条同名内容。

客户端统一使用“服务器身份 + 账号身份 + 逻辑媒体 ID”，并将本地媒体源单独命名。复用现有 session 命名空间思路，但同一 NAS 的内网/外网地址应映射到同一服务器身份；还需支持没有新身份能力的旧服务器。

### 状态存储与同步

现有 DataStore 适合设置和少量键值，不宜把数万条历史、合集成员和下载任务塞进一个不断改写的 JSON。建议为这些结构化数据引入一个本地 SQLite 存储层，是否采用 Room 以迁移原型决定，不要求全项目改架构。

服务端采用独立用户状态表，接口支持分页和幂等写入。收藏删除保留同步所需的删除记录；观看状态与进度分别定义冲突规则；下载字节只在本机，完成播放后的观看状态才同步。登录切换要明确哪些私有离线数据保留，已导出系统相册的副本不由退出登录操作擅自删除。

新增能力通过 ServerCaps 协商：新客户端连接旧服务端时保留原有浏览/续播能力，给出“此服务端暂不支持”的明确说明。

### 控制后台成本

- 新列表使用服务端分页，不扫描整库；收藏/历史只在变化时增量同步。
- 下载默认低并发，并与现有播放优先调度协作，避免长时间下载让存储优化整晚被暂停。
- 缩略图、章节预览按需生成；不增加全库视频帧预热，不把任意智能合集都展开成大量随机预热任务。
- 手机不承担整库后台 AI 分析；用户关注提醒采用增量版本或低频查询。

## 9. 交付顺序与投入估计

估计单位为一名熟悉代码的开发者的工作日，包含实现、迁移、异常处理与必要验证；属于规划量级，不是排期承诺。接口重构、旧数据迁移和系统兼容问题可能扩大范围，各行不可机械相加。

| 迭代 | 交付内容 | 粗估投入 | 完成门槛 |
|---|---|---|---|
| M0 | 稳定媒体身份、用户状态模型、旧服务端降级的小原型 | 3–5 人日 | 替换/改名后关联保持；迁移可验证 |
| M1 | 收藏/合集、继续观看、首批多选 | 12–20 人日 | 核心链路完整，跨账号隔离，数量可对账 |
| M2 | 原文件离线下载中心 | 12–20 人日 | 断网/杀进程/重启/源文件变化场景通过 |
| M3 | 组合检索/保存筛选、外置字幕和延迟 | 10–18 人日 | 查询正确、旧服务端兼容、字幕格式验证 |
| M4 | 按实际使用反馈选书签、轮播、应用锁或播放队列 | 每项约 3–8 人日 | 逐项验收，不一次堆入所有功能 |

建议先落地 M0 + M1，并用实际使用反馈决定 M2 与 M3 的先后。若用户经常出门或网络不稳定，下载中心提前；若主要在家浏览超大库，组合搜索提前。投屏先做能力原型，不挤占首批功能。

## 10. 验收与发布

功能验证覆盖深/浅主题、长中文文件名、较大系统字号、横屏/窄屏，以及本地模式、旧服务端、多服务器与账号切换。

用户状态和下载优先测试进程重建、断网、存储不足、文件替换及数据库迁移。后台服务、真实 URI 授权、系统通知和生物识别使用原生集成验证；纯前端演示不能替代这些检查。

性能以当前真实大库基线对比首屏、滚动和查询耗时，不在没有测量前承诺固定毫秒数。没有待处理任务时不增加高频轮询或整库扫描。

实施后按现有偏好交付固定发布密钥签名的正式 APK，验证成功后只保留最新正式安装包；不在这次方案调研中改动发布版本或重新编译。
