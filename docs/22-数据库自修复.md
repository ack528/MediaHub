# 数据库自修复

服务启动时，在取得数据目录进程锁之后、迁移和后台任务开始之前，对数据库执行完整的 `PRAGMA integrity_check`，并检查全文搜索索引与媒体记录是否一致。`quick_check` 不能检测普通索引缺记录，因此不用于代替完整检查。大型数据库的启动检查会增加启动时间，进度和结果写入服务日志。

检测到损坏或搜索索引不一致时：

1. 用 SQLite 页级备份 API 保存修复前的已提交数据库，包括 WAL 中尚未检查点写回的数据。文件位于 `<数据目录>\repair\before-repair-*.sqlite`。该目录独立于日常备份，不参加自动轮换，需自行保管与清理；副本包含账号和令牌等敏感信息。
2. 在同一个写事务中重建普通索引，并从 `media` 表重建 `media_fts`。包括 `ix_m_gen` 缺记录与全文索引同时损坏的情况。
3. 再次检查数据库完整性、全文索引内部结构与媒体记录的一致性，全部通过才提交并启动服务。

保存副本失败则不修复。数据表或结构损坏到不能通过重建索引恢复时，修复事务回滚，服务退出并记录错误及副本位置。不会清空媒体库、删除账号和历史，也不会自动换成较旧的备份。此功能不能保证恢复所有损坏，也不能消除磁盘、内存或底层数据库引擎导致的潜在问题。

全量扫描、增量扫描或其元数据补全遇到 SQLite 损坏错误（包括扩展错误码 779）时，服务停止重复扫描，安排一次正常重启，在下次启动时执行上述修复。重启使用已有的 Windows 安装路径和配置文件；不能启动重启助手时，服务停止并提示手动启动。普通的锁忙、磁盘已满和 I/O 错误不会触发索引重建。

日常自动备份先写入临时文件，检查完整性与全文索引一致性，通过后才加入可还原列表并轮换旧备份。验证失败的备份不会替换旧备份。修复前副本不等同于通过验证的可用备份。

不需要额外安装 sqlite3；检查和修复使用服务端已有的 SQLite 驱动。升级到包含此功能的服务端后，正常启动即可触发检查。
