# 转场动画研究:B 站 / 小红书「点哪里从哪里展开」是怎么做的

> 2026-10-18。素材是用户录的两段手机屏幕录像(`D:\Program Files\Netease\GameViewer\Download\2806.mp4` 小红书、`2807.mp4` B 站),
> 1080×1620、可变帧率(平均约 115 fps,帧间隔 3~41 ms,按每帧的真实时间戳量),各 7~8 秒,每段有 3 次左右的「点开 / 返回」。
> 目的:看清它们的动画到底是不是线性的、背景做了什么,再对照我们现在的实现(`ui/Hero.kt`)找出「速度和感觉不对」的原因。

## 一、方法

1. 解码每一帧,用帧间差找出画面在动的时间段,得到每次转场的起止(`seg.py`)。
2. 把转场区间逐帧(每帧一格)排成联系表,配上 5% 的坐标网格,**手读**容器(展开中的卡片)四条边的位置;
   B 站的黑色视频区、纯白页面可以自动量(`bili_measure.py`),早期几帧(卡片内容和页面内容叠在一起)只能手读。
3. 背景:追踪背景里一张大图的四条边(半强度位置,亚像素,`edge_track.py`)得到缩放和位移;
   用平均亮度比得到变暗;用梯度能量和「清晰帧按不同半径糊开」对比,得到等效高斯模糊半径(误差约 ±20%)。
4. 把「完成度」曲线(0 = 起点,1 = 终点)拿去拟合贝塞尔曲线和弹簧(`fit.py`)。

时间 0 取「画面第一次出现运动」的那一帧(点击到画面开始动之间还有大约 10 ms,这里不算)。

## 二、结论一览

| 问题 | 结论 |
| --- | --- |
| 是线性的吗? | **不是**。打开是强减速曲线(开头就最快,有一条很长的尾巴);返回是起步稍慢的缓动,中段近似匀速,再减速 |
| 总时长 | 打开约 **300 ms 到 95%**(视觉上 330 ms 落定);返回约 **300 ms 到 95%**,350 ms 落定。B 站 6 次转场 290~375 ms,小红书 4 次 275~360 ms,两家几乎一样 |
| 两家曲线 | 打开的位置曲线 **B 站和小红书几乎重合**(同一条曲线);四条边用的是同一个进度(右 / 上 / 左边一致,下边 B 站略滞后) |
| 动的是什么 | 不是「一张图放大」,而是一个**容器**:矩形从被点的卡片位置变到整屏,内容在容器里**重新排版**(页面内容)或被**等比放大**(卡片快照),两者交叉淡化 |
| 背景 | 同时做三件事:**整体缩小**(到约 0.905 倍,缩放中心是屏幕中心)、**高斯模糊**(到 σ≈28 px@1080 宽)、**压暗**(黑色遮罩 α≈0.235)。返回时反着来,全部跟着容器进度走 |
| 圆角 | 整个过程圆角都很大(约 20~25 dp),不是「从卡片圆角线性变到 0」,到最后几帧才收小 |
| 卡片本身 | 被点的那张卡片在容器出现后从列表里消失(被容器「拿走」),返回时容器落回去 |

## 三、打开:逐帧数据

### 3.1 容器边缘的完成度(0 → 1,距离第一次运动的毫秒数)

左 / 上 / 右边按「起点 → 屏幕边缘」算。两家的数据放在一起:

| 时间 ms | 完成度 | | 时间 ms | 完成度 |
| ---: | ---: | --- | ---: | ---: |
| 14 | 0.04 | | 138 | 0.70 |
| 39 | 0.18 | | 162 | 0.77 |
| 66 | 0.34 | | 188 | 0.82 |
| 89 | 0.48 | | 213 | 0.87 |
| 104 | 0.55 | | 248 | 0.91 |
| 121 | 0.62~0.64 | | 281 | 0.94 |
| 129 | 0.67 | | 312 | 0.96 |

要点:
- 50% 在约 100 ms,80% 在约 190 ms,95% 在约 300 ms。**前 1/3 的时间走了一半的路**。
- 速度在 40~90 ms 达到峰值(约每毫秒走 0.6%),之后一路减速,150 ms 之后每 25 ms 只走 8% → 5% → 3%。
- 最开始(0~15 ms)几乎不动,然后立刻进入最快段,所以没有「慢慢起步」的感觉。

### 3.2 拟合

- **贝塞尔**:`cubic-bezier(0.25, 0.60, 0.20, 1.00)`,延迟约 5 ms,时长 480 ms,均方根误差 0.009。
  (只是数学上的最佳拟合;480 ms 里最后 150 ms 只走最后 5%,肉眼看不出来。)
- **弹簧**:阻尼比 **ζ ≈ 1.2**(略过阻尼,没有过冲),**ω ≈ 20.5 rad/s**(Compose 的 `stiffness = ω² ≈ 420`),均方根误差 0.010。
- 对照常见曲线(各自取最佳延迟和时长):easeOutCubic(0.215,0.61,0.355,1)@420 ms 误差 0.014 最接近;Material standard(0.2,0,0,1)@440 ms 误差 0.023;
  Material 强调减速(0.05,0.7,0.1,1)误差 0.08(**差很多**:它在前 30% 的时间就走了 80%,比实测的快得多);easeInOut 误差 0.10;线性 0.064。

> **没有过冲**:没看到容器超过终点再回来(完成度从不超过 1)。所以不能用 ζ<1 的弹簧。

### 3.3 容器的形状

- 起点就是被点卡片的整个矩形(含标题 / 点赞行),不是只有缩略图。
- 小红书:卡片在左列,容器的**左边几乎不动**(卡片左边距 1.2% → 0.5%),右 / 上 / 下边向外扩;上边、右边、下边用同一个完成度。
- B 站:卡片在右列,容器的**右边几乎不动**(97.5% → 99.5%),左 / 上边向外扩。下边比其它边慢一点(完成度滞后约 0.1~0.15),因为 B 站播放器区域(黑色)的高度是从缩略图高度变到 16:9 区域,下面的白色页面是「露出来」的。
- 圆角:约 20~25 dp(1080 宽时 5~6% 屏宽)在整个过程里保持,到 p>0.9 才开始收小;最后一帧仍能看到屏幕圆角。

### 3.4 内容怎么过渡

- **卡片内容**(缩略图 + 标题 + 点赞)是被**等比放大**的快照:小红书 58 ms 时容器宽 46%(卡片 31.6% 的 1.46 倍),标题字号跟着变大。
- **页面内容**是在容器当前尺寸下**重新排版**的真页面(图片宽度、右上角的 logo、关注按钮都贴着容器边,不是缩小的整页)。
- 两者**线性交叉淡化**,窗口很短:从约 55~75 ms(完成度 0.25~0.3)开始,持续约 **45 ms**,到完成度 0.5~0.6 时页面已完全替代卡片。
  过渡中容器整体发灰(两层半透明叠在一起),这是正常的。
- 页面的数据(图片 / 评论)是之后才加载的:小红书在 300 ms 左右图片区会空白一下再出来,B 站先出黑色播放器和骨架屏。**它们也有「空」的瞬间,但只在页面内部,容器和标题栏不闪**。

### 3.5 背景(这就是「背景对应的缩放」)

三个量都是同一时间轴上的:

| 时间 ms(距第一次运动) | 缩放(小红书照片边缘) | 亮度(B 站 / 小红书) | 模糊 σ(1080 px,B 站 / 小红书) |
| ---: | ---: | ---: | ---: |
| 0 | 1.000 | 1.00 / 1.00 | 0 / 0 |
| 29~39 | 0.989 | 0.99 / 0.99 | 1.1 / 0.8 |
| 71~78 | 0.965 | 0.92 / 0.96 | 7 / 6 |
| 88~101 | 0.956 | 0.89 / 0.93 | 12 / 9 |
| 114~126 | 0.943 | 0.86 / 0.90 | 20 / 13 |
| 154 | ~0.93 | 0.83 / 0.88 | 27 / 16 |
| 196 | 0.905 | (0.815@174)| 28 / — |

- **缩放**:四条边(上、右,以及 B 站横幅的上下)都能对上「以屏幕中心为中心的等比缩放」,中心估计为 (0.51, 0.50)。
  缩放量 `s = 1 − 0.095·p`(p 是容器完成度),即**最终约 0.905**。整个过程中 s 与 p 的比例稳定(0.09~0.11)。
- **模糊**:B 站约 30 ms 开始、170 ms 达到最大 σ≈28 px(1080 宽,即屏宽的 2.6%;按 3× 密度约 9~10 dp),之间近似线性;小红书同样的形状但幅度小一点(150 ms 时 16 px,最终约 20~25)。
- **压暗**:B 站亮度 = 1 − 0.235·p(最终约 0.765,即黑色遮罩 α≈0.23);小红书的背景白色居多,量到的下降比较慢,最终估计 0.78~0.8。
- 背景整个是一层:缩放、模糊、压暗一起作用在整页列表上(不是只给被点的卡片周围),顶部状态栏 / 灵动岛不跟着缩放。

| ---: | ---: | --- | ---: | ---: |

- 比打开**慢起步**:先有大约 25 ms 的延迟,然后速度从 0 升到约 0.5%/ms,在 50~120 ms 之间近似**匀速**,再减速。
- 拟合:`cubic-bezier(0.30, 0.40, 0.40, 0.95)`,延迟 25 ms,时长 340 ms,均方根误差 0.004;iOS ease-out(0,0,0.58,1)@300 ms 误差 0.017 也可接受。
- **不是打开的时间反演**:返回时容器是从整屏**先从左上角收缩**(左边、上边先动,右边在前 100 ms 几乎不动,贴着屏幕右边),再整体滑向卡片位置;
  同时内容从页面淡成卡片快照(中段,完成度 0.35~0.6),卡片快照最后落在原位。
- 背景全部跟着容器完成度**线性**恢复:模糊 σ = 28·(1−p)、压暗 = 0.235·(1−p)、缩放 = 1 − 0.095·(1−p)(实测 124 ms:模糊 15、亮度 0.884、缩放≈0.95,和公式 14 / 0.882 / 0.952 吻合;198 ms:5.0 / 0.945 / 0.98 vs 5.6 / 0.953 / 0.981)。
  这些背景效果比容器更早结束的错觉来自曲线:p 过了 0.9 之后背景已经看不出和原来的区别。

## 四点五、漏掉的一点:下一个界面在动画里就是加载好的真页面(用户指出,复看小红书录像确认)

- 小红书点开:容器从第 55 ms 起显示的就是**真正的笔记页**(头像、关注按钮、图片、正文、底部评论栏都在,按容器当前大小排版),
  不是一张替身图;动画结束时也**没有任何"换成真页面"的瞬间**——容器长到全屏,就已经是那个页面了。
- 小红书返回:收回的容器里一直是笔记页本身在缩小(内容还是活的),下面的瀑布流也是现成的(没有重新加载、没有空白),
  容器落回卡片的同时内容淡成卡片。
- B 站同理:打开时容器里就是播放页(黑色播放器区 + 下面的骨架屏 / 简介),返回时是播放页本身在收回。
- **对我们的意义**:3.3.0 ~ 3.3.2 的做法是"先画一张缩略图的覆盖层做动画,动画完再把查看器换上来"(交接),
  交接这一下就是"标题闪一下"的根源;再加上覆盖层最后被拉成全黑,闪得更明显。正确的做法是**查看器从第一帧就组合**,
  放在动画容器里裁剪 / 缩放,动画结束什么都不用换。
- **返回抖动的根源**:打开后列表停在 0.905 倍,缩略图位置是在缩小状态下记的;返回时背景放大回 1,容器却落向缩小时的旧位置,
  最后一帧跳到真实位置。正确做法是记"列表自己坐标系里的位置",每一帧按背景当前缩放换算目标。

## 五、对照我们现在的实现(`ui/Hero.kt`、`ui/Motion.kt`)

| 项 | 我们现在 | 实测的 B 站 / 小红书 |
| --- | --- | --- |
| 打开曲线 | `spring(dampingRatio=0.86, stiffness=420)` | ζ≈1.2、ω²≈420。**我们的 ζ=0.86 会过冲约 0.6%**(容器超出全屏再弹回,看起来是「晃」),而且阻尼不足让收尾变长 |
| 返回曲线 | `spring(0.9, 480)` | 慢起步贝塞尔(0.30,0.40,0.40,0.95)≈340 ms,延迟 25 ms。我们是一上来就最快 |
| 容器的内容 | 只画一张缩略图(铺满裁剪)+ 到全屏才交接给查看器 | 卡片内容 → 页面内容交叉淡化(约 45 ms),页面内容在容器内重新排版 |
| 背景 | 一块黑色遮罩 `alpha = k`(0 → 1,最后全黑),列表不缩放不模糊 | 列表缩放到 0.905、模糊 28 px、压暗 0.235,**不是全黑** |
| 圆角 | 从卡片圆角线性变到 0 | 整个过程保持 ~22 dp,收尾才收小 |
| 被点的卡片 | 查看器打开期间隐藏 | 相同 ✓ |

感觉不对的主要原因:
1. 曲线形状:我们没有「前 1/3 时间走一半」的减速感,而且有过冲。
2. 背景:黑色渐黑 + 没有缩放 / 模糊,层次感全无;B 站 / 小红书的背景退后是「景深」的效果。
3. 容器里没有内容过渡,只有一张图在放大,所以不像「页面从卡片里长出来」。
4. 返回时起步太猛。

## 六、实现方案(3.3.3 已按此重写,见 ui/Hero.kt)

1. **曲线**:打开用 `spring(dampingRatio = 1.2f, stiffness = 420f)`(无过冲);返回用 `tween(340, easing = CubicBezierEasing(0.30f, 0.40f, 0.40f, 0.95f))`,延迟约 25 ms。
   手势返回时由手指进度驱动,松手后用同一条返回曲线从当前位置接着走。
2. **容器**:矩形从卡片位置到整屏,四条边同一个完成度;圆角 22 dp 保持到 p>0.9 再过渡到 0(或屏幕圆角)。
3. **内容**:容器内先显示卡片快照(等比放大),p 从 0.25 起 45 ms 线性交叉淡化为页面(查看器内容放在容器里,按容器尺寸排版;图片在容器内保持原图比例居中)。
   第一阶段可以只做「卡片快照 → 缩略图铺满的查看器」的交叉淡化,不重排。
4. **背景**:把列表(`ChatScreen` / `SearchScreen` / `RandomScreen` 的根)包一层 `graphicsLayer`,按容器完成度 p 驱动:
   `scale = 1 − 0.095·p`(`transformOrigin` = 屏幕中心)、`RenderEffect.createBlurEffect(σ = 2.6% 屏宽·b(t))`(Android 12+;更早的系统跳过模糊)、`scrim α = 0.235·p`;
   模糊走自己的线性时间轴(约 30~170 ms)。Android 11 及以下没有 `RenderEffect`,只做缩放和压暗。
5. **验证**:用同样的方法(录屏 → 逐帧量)对我们自己的实现再测一遍,和上面的表对。

## 七、不确定的地方

- 只录了一部手机、一台机器上的一段录像,每个 App 只量了 1 次打开 + 1 次返回(其它几次只量了时长,都在 275~375 ms)。
- 边缘位置的手读误差约 ±2% 屏宽;早期几帧(卡片内容和页面叠着)误差更大。
- 模糊半径是用梯度能量反推的,误差约 ±20%;亮度用的是背景条带的平均值,小红书白底占比大,比 B 站低估。
- 没法区分「弹簧」和「贝塞尔」(两者在这个精度下拟合一样好),按易实现、可打断的角度选弹簧。
- 下边缘的滞后(B 站)、返回时右边缘的行为没有做成公式。

## 八、3.3.4:跟手、打断、去黑块(用户录屏 23478.mp4 反馈)

- 现象:侧滑返回时屏幕边出现 ROM 自己的返回箭头,查看器纹丝不动,松手后才开始收回 —— 这类 ROM 的返回手势只在松手时发一个"返回",
  不把进度交给应用(`PredictiveBackHandler` 收不到进度),所以"严重不跟手"。另外打开 / 返回时一整块黑色圆角矩形(图片上下的黑边)
  在浅色列表上展开收回,看起来就是闪。
- 参考的开源方案:Zoomable(mxalbert1996,Compose,自带竖直拖拽关闭,但要换掉 telephoto,失去超大图分块解码)、
  StfalconImageViewer / DragToDismissImageViewer(View 体系,"图片跟手 + 背景随距离变淡 + 松手超阈值飞回原位,否则弹回")、
  Telegram PhotoViewer(同样的手势,关闭时图片飞回原来的位置)。结论:保留 telephoto,在外层自己实现同样的手势。
- 做法:外层在 Initial 阶段先看手势 —— 竖直方向(|dy| > 1.3|dx|)且图片没放大才接管(横滑留给翻页,双指留给缩放);
  图片跟手位移、按拖出距离缩小到最多 0.65,黑色背景按距离变淡(拖半屏的 60% 就全透明),列表的缩放 / 模糊 / 压暗同步恢复;
  松手 |dy| > 8% 屏高或速度 > 900 px/s 就从当前位置收回(返回动画以松手时的图片位置为起点),否则弹簧弹回,弹回途中能再抓住。
- 打断:打开中返回不再等,`Animatable` 从当前值改朝 0 走(临界阻尼弹簧,带惯性);拖拽弹回用可取消的协程。
- 去黑块:动画中只裁出图片本身(从缩略图位置 / 圆角到全屏居中的图片框),查看器的黑色背景单独按进度淡入淡出。
