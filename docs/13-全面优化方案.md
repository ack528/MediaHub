# 13 · 全面优化方案(3.1.1 之后)

> 写于 2026-10-18,对应手机端 / 服务端 / 管理程序 3.1.1。
> 方法:逐个模块读当前代码,找出瓶颈和缺口;再对照 65 个同类开源项目 / 工具(媒体服务器、相册、播放器、图片处理、内网穿透、索引、工程化),看它们怎么解决同样的问题。
> 每一项都写了**现状(带代码位置)→ 怎么改 → 预期收益 → 成本 / 风险 → 怎么验证**。标「公开资料」的数字来自对方的文档或博客,**没有在本项目里实测**;落地时要用文末的验证方法自己测。

## 0. 结论:最值得先做的 10 件事

## 1. 现状快照

| 部分 | 规模 | 已经做得好的 |
|---|---|---|
| 服务端 `server/` | Go 约 1.6 万行(含测试),纯 Go SQLite(WAL + FTS5 trigram) | 三阶段扫描可续扫、NTFS 文件 ID、每盘缓存 + LRU、按需 HLS 转码(QSV、H.265、码率上限、预热)、WebP 缩略图、gzip、测速、去重 / 压缩 / 回收区、内网穿透托管、客户端优先调度、自动更新(镜像 + DoH) |
| 手机端 `android/` | Kotlin 约 1.2 万行,Compose + Coil 3 + Media3 1.11 + Paging 3 | 接口 / 媒体分两个 OkHttp 客户端、HTTP/2 PING、证书指纹固定、内网直连、自动画质、超分 / 补帧 / HDR 渲染管线、本地媒体模式 |
| 管理程序 `desktop/` | Tauri 2 + React | 配置项由 schema 生成、各功能页、托盘 |
| 构建 | `tools\build-guard.ps1`、`package.ps1 -Both` | CPU 监测 + 卡死重试;三端并行,两套产物一次出(暖缓存 63 秒) |

读代码时发现的主要缺口(下面各节展开):

- 安全:`api.go` 登录失败只 `time.Sleep(s.LoginDelay)`(1 秒),没有按 IP / 账号计数和封禁;服务现在可以经 frp 暴露到公网。
- 缩略图:`render.go` 的 `Renderer.sem` 固定 2 张并发,每张图起一个 ffmpeg 进程,JPEG 是全尺寸解码后再缩小。
- 手机端:`Models.kt` 里有 `thumbhash` 字段,但界面从来没用;直放视频没有 `CacheDataSource`;release 关闭了 R8,也没有 Baseline Profile。
- 播放:能不能直放靠"先试,解码失败再转码"(`VideoPlayer.kt` 的 `onPlayerError`);一旦转码,视频一定重编码,没有"视频直接复制、只转音频"的路径。
- 索引:`index.go` 每次扫描都遍历全部目录并逐个 upsert 文件;没有变更通知,新文件要等下次定时扫描(默认 24 小时)。
- 数据库:`store.go` 只设了 WAL / synchronous / busy_timeout,没有 `mmap_size`、`cache_size`、`PRAGMA optimize`;没有自动备份。
- 搜索:`history.go` 的搜索分页用 `LIMIT ? OFFSET ?`,翻得越深越慢;结果固定按时间排,没有相关度。
- 管理程序:各页 1~3 秒轮询一次(`Optimize.tsx` 1 秒、`Clients.tsx` 2 秒…)。
- 工程:没有 CI;没有 `pprof`;最大的几个文件 `VideoPlayer.kt`(1471 行)、`SettingsScreen.kt`(1245 行)、`VideoRenderer.kt`(1193 行)。

## 3. 优化项详述

### 3.1 安全(S)—— 服务现在可以暴露到公网,优先级最高

**S1 登录防爆破 + 可选两步验证**(P0,2 天)
- 现状:`api.go` 登录失败只睡 `LoginDelay`(1 秒)。经 frp 进来的请求在服务端看来来源是 127.0.0.1(`clients.go` 把回环归为 tunnel 线路),按 IP 封禁会把所有穿透用户一起封掉。
- 做法:
  1. 计数键 = 账号名 + 线路(lan / tunnel / wan)+ IP;frp 代理里打开 `transport.proxyProtocolVersion = "v2"` 后服务端可以拿到真实来源 IP(需要服务端解析 PROXY 协议头,frpc 配置里加一行)。
  2. 失败退避:同一个键连续失败 5 次后锁 1 分钟,之后每次翻倍,最长 1 小时;成功一次清零。锁定期间直接返回 429,不做密码计算(pbkdf2 本身就耗 CPU,反复算等于给爆破者送资源)。
  3. 管理程序「客户端连接」页加「最近登录失败」列表和「解除锁定」按钮。
  4. 可选 TOTP(RFC 6238,纯标准库实现约 60 行):管理程序里生成二维码,手机登录界面多一个 6 位验证码输入框;**只对非内网线路要求**,在家不用输。
- 参考:Vaultwarden、CrowdSec / fail2ban、Authelia。
- 验证:单元测试模拟 20 次错误密码,第 6 次起 429 且耗时 < 5 ms;正确密码在锁定期外能登录。

**S2 穿透线路默认更严**(P1,0.5 天)
- 经 tunnel / wan 进来的请求:禁用 `/speedtest/up` 之类的大上传接口、限制单令牌并发流数量(比如 4),防止令牌泄露后被拿去跑流量。
- 令牌在穿透线路上默认 30 天过期(内网保持现在的长期有效)。

### 3.2 图片与缩略图(I)

**I1 thumbhash 占位图**(P0,0.5 天)
- 现状:服务端 `poster.go` 生成并存了 `thumbhash`,`items.go` / `dialogs.go` 都返回了,手机端 `Models.kt:103` 有字段但界面没用,加载中显示纯色块。
- 做法:按 ThumbHash 的参考实现(有 Java 版,MIT)写一个 Kotlin 解码函数 → 生成 32×32 左右的小位图 → 作为 Coil 请求的 `placeholder`。解码结果按 media id 放进一个小的 LRU(几百个就够)。
- 收益:滑动时格子先出模糊的色块轮廓,原图到了淡入;和 Telegram 的 minithumbnail 观感一致。几乎不占流量(每项 20~30 字节,已经在 JSON 里了)。
- 验证:开发者选项"网络限速"或经穿透时录屏对比。

**I2 缩略图生成提速**(P0,1 天)
- 现状:`render.go` 每张图起一个 ffmpeg 进程、全尺寸解码再缩小;同时最多 2 张(`sem: make(chan struct{}, 2)`)。一张 4000 万像素的 JPEG 全尺寸解码就要几百毫秒,Windows 上起一个进程本身还要几十毫秒。
- 做法(按收益排):
  1. **JPEG 缩小解码**:目标宽度 ≤ 原图 1/2、1/4、1/8 时给 ffmpeg 加 `-lowres 1/2/3`(MJPEG 解码器在 DCT 阶段直接出小图),解码量降到 1/4 ~ 1/64。或者对 JPEG 改用已随包的 libvips `vips thumbnail`(自带缩小解码 + 自动旋转)。两种都先做对比测试再选。
  2. **并发随核数和调度级别变化**:Idle 时 `min(核数/2, 6)`,Active 时 2,Streaming 时 1(接 `governor`)。
  3. **小档位直接用 EXIF 内嵌缩略图**:相机 / 手机照片的 EXIF 里通常有 160 × 120 的 JPEG 缩略图,240 档以下可以直接取(ExifTool `-b -ThumbnailImage`,已经有 `renderRaw` 的同类代码),比解码原图快两个数量级;取不到再走正常流程。
  4. 扫描结束后对**最近 30 天新增**和**最近浏览过的群组**在 Idle 时预热 240 / 480 档(docs/12 里列为"日后可以做")。
- 参考:libvips、imgproxy、Immich、FFmpeg。
- 验证:准备 200 张不同尺寸 JPEG,清空缓存,分别测"全部生成完的总耗时"和"单张 p95";目标总耗时降到 1/2 以下。

**I3 渐进式 / 高清晰度切换**(P2,1 天)
- 查看器打开大图时先显示已缓存的 720 / 960 档,原图到了再替换(Telegram 的做法),减少"点开大图白屏等待"。Telephoto 支持先给低清再给高清的子采样源。

### 3.3 视频播放(V)

**V1 设备能力协商 + 只转需要转的部分**(P0,3~4 天)
- 现状:先试原画,`onPlayerError` 收到解码错误再改走 HLS;一旦走 HLS,`hls.go` 总是重新编码视频。常见的"视频手机能解、只是音频(DTS / TrueHD / 部分 AC3)或封装(AVI、部分 MKV)不支持"的片子,也要整条重编码:费 CPU / 核显、画质有损、起播慢。另外有的手机遇到不支持的音频会**静音播放而不报错**,用户以为片子没声音。
- 做法:
  1. 手机端启动时用 `MediaCodecList` 收集能力:各视频编码的最高 profile / level / 分辨率 / 帧率、HDR 类型、音频编码列表,缓存起来,播放请求时带上(或登录时上报一次,服务端按令牌记住)。
  2. 服务端已经有每个文件的 `vcodec`、`acodecs`、`container`、`bitrate`、`hdr`(`items.go`),按能力做四选一:**直放** / **封装转换**(`-c copy` 转成 MP4 或 TS)/ **只转音频**(`-c:v copy -c:a aac`)/ **完整转码**。决定和原因写进播放接口的返回值,播放器信息面板显示"为什么转码"(Jellyfin 的仪表盘也这么做)。
  3. 封装转换和只转音频时,HLS 分段要按源文件的关键帧切(`-c:v copy` 不能强制关键帧),播放列表要用 ffprobe 读出的关键帧时间生成,不能再固定 4 秒;实现上可以先只支持"从头播 + 段内拖动",拖动到很远的地方时退回完整转码。
  4. 保留现在的"失败再转码"作为兜底。
- 收益:这类片子转码 CPU 从"一个核显编码器满载"降到几乎 0,画质无损,起播少一次失败往返。
- 参考:Jellyfin DeviceProfile 与 `EnablePlaybackRemuxing`、Jellyfin Android 的 ffmpeg 音频扩展、Findroid。
- 风险:能力探测在少数机型上不准(Jellyfin 论坛有 HEVC level 判断过严导致误转码的例子)→ 能力表要允许手动覆盖("此设备支持 HEVC 10-bit"开关),而且保留失败兜底。
- 验证:准备 MKV(H.264 + DTS)、AVI(MPEG-4)、MP4(HEVC + TrueHD)样本,记录起播时间、服务端 CPU / 核显占用、是否有声音。

**V2 直放视频磁盘缓存 + 下一个预加载**(P0,1.5 天)
- 现状:`Playback.kt` 只配置了 `DefaultLoadControl`,直放视频没有磁盘缓存,往回拖、看第二遍都要重新下载;经穿透时尤其明显。
- 做法:
  1. `SimpleCache`(LRU,默认 1 GB,可在设置里调)+ `CacheDataSource` 包在现有的 OkHttp 数据源外面;缓存键用 media id + 文件指纹(`size:mtime`),文件变了自动失效。HLS 转码段不缓存(本来就是临时的)。
  2. `DefaultPreloadManager` 给翻页器的前后各一个直放视频预加载前 3~5 秒(只在 Wi-Fi / 内网直连时开,移动网络关闭)。
- 参考:Media3 `CacheDataSource`、`DefaultPreloadManager`(1.4 起提供)、NewPipe。
- 验证:同一视频看完再从头看,第二遍网络流量 ≈ 0;翻到下一个直放视频首帧时间。

**V3 HLS 改 fMP4 分段**(P1,1.5 天)
- 现状:`hls.go` 用 `-hls_segment_type mpegts`,4 秒一段。
- 做法:H.265 转码改用 `-hls_segment_type fmp4`(带 `init.mp4`);H.264 可以保持 TS 或一起换。播放列表加 `#EXT-X-MAP`。
- 收益:Jellyfin 团队的说法是 fMP4 才能稳定用上 HEVC / AV1;TS 里的 HEVC 在部分解码器上首帧慢或有花屏。每段的封装开销也比 TS 小(TS 每 188 字节一个包头)。
- 风险:按需分段 + 拖动重启 ffmpeg 的逻辑要确认 fMP4 的时间戳连续(`-hls_fmp4_init_filename`、`-hls_segment_options movflags=+frag_discont`)。先在测试里覆盖"拖动到第 50 段再播"的情形。

**V4 进度条预览图(trickplay)**(P1,1.5 天)
- 做法:governor 空闲时,对视频按每 10 秒一帧(`-skip_frame nokey` 只解关键帧,快很多)生成 10 × 10 的精灵图(每格 240 宽,WebP),存到各盘 `.mediahub\trickplay\`;接口返回精灵图地址和每格对应的时间。手机拖动进度条时在指针上方显示对应格子。
- 收益:长视频拖动定位快很多,不用拖过去等缓冲才知道到了哪。
- 参考:Jellyfin 10.9 trickplay(公开资料:每部电影约 50~100 MB,可以只对时长 > 5 分钟的视频生成、按缓存配额管理)、Stash 的预览精灵图。

**V5 外挂字幕**(P1,1 天;ASS 特效渲染另算)
- 现状:直放时 ExoPlayer 能显示内嵌字幕;同目录的 `.srt` / `.ass` / `.vtt` 不会被加载;走 HLS 转码时内嵌字幕也丢了。
- 做法:扫描时记录同名字幕文件(`片名.srt`、`片名.zh.ass` 等),播放接口返回字幕列表,手机端用 `MediaItem.SubtitleConfiguration` 加载;转码时把内嵌字幕抽成 WebVTT 单独提供。字符编码(GBK 字幕很常见)在服务端转成 UTF-8。
- ASS 特效(位置、动画):ExoPlayer 只按普通文本显示。要完整效果得引入 libass(mpv-android 的做法),工作量大,列为 P2。

### 3.4 索引与数据库(D)

**D1 实时增量索引**(P1,3 天)
- 现状:`index.go` 的 `ScanRoot` 每次都遍历所有目录、逐个文件 upsert;新文件要等 `scan.intervalHours`(默认 24 小时)或手动重扫。
- 做法:
  1. **目录变更通知**:每个根目录开一个 `ReadDirectoryChangesW`(fsnotify 或直接调 Windows API,项目已经在用 `golang.org/x/sys/windows`),收到事件后去抖 3~5 秒,只重扫涉及的那几个目录(复用 `ScanRoot` 里"扫一个目录"的逻辑)。网络盘 / 监视失败时自动退回定时扫描。
  2. **USN 日志加速全量扫描**(可选,收益在几十万文件以上才明显):记下上次扫描结束时的 USN,下次只读这之后的变更记录,得到"变了哪些文件",不用遍历全盘。需要管理员权限读卷的 USN 日志,做成可选项;拿不到权限就用现在的遍历。
  3. 全量扫描保留为每周一次兜底(Syncthing 也是"监视 + 定期全量")。
- 参考:Everything(MFT + USN)、Syncthing、fsnotify、Navidrome / Kavita 的目录监视。
- 风险:大量文件同时拷入时事件风暴 → 去抖 + 合并到目录级 + 走 governor 让路。
- 验证:往库里拷 100 张照片,计时到手机能看到;拷 1 万张时观察 CPU 和是否丢事件(最后一次全量扫描对账)。

**D2 SQLite 调优**(P0,0.5 天)
- 现状:`store.go` DSN 只有 WAL、`synchronous(NORMAL)`、`foreign_keys`、`busy_timeout`,`SetMaxOpenConns(32)`,所有连接都是 `_txlock=immediate`。
- 做法:
  1. 加 `mmap_size(268435456)`(256 MB)、`cache_size(-65536)`(64 MB)、`temp_store(MEMORY)`。
  2. 读写分离:一个只读连接池(`mode=ro`,deferred 事务,可多连接)给浏览接口,一个只有 1 条连接的写池给扫描 / 状态保存。现在 32 个连接都以 IMMEDIATE 开事务,读请求也可能排在写锁后面。
  3. 每次扫描结束、以及每天一次执行 `PRAGMA optimize`(更新统计信息,让查询计划选对索引)。
- 验证:用 10 万条测试数据测 `history` 首屏和翻页的 p95,扫描进行中再测一次。

**D3 每日自动备份数据库**(P0,0.5 天)
- 现状:账号、令牌、播放进度、浏览位置、压缩队列都在一个 SQLite 文件里,没有备份。
- 做法:每天空闲时 `VACUUM INTO '<数据目录>\backup\mediahub-YYYYMMDD.db'`(在线、一致、不阻塞读),保留最近 7 份;管理程序「关于」页显示最近一次备份时间,加"立即备份"和"从备份还原"(还原 = 停服务、替换文件、重启)。
- 参考:Immich 每晚自动备份数据库、Litestream。

**D4 搜索分页改游标**(P1,0.5 天)
- 现状:`history.go:416` 起的搜索用 `cursor` 当 OFFSET,`LIMIT ? OFFSET ?`;越往后翻越慢,而且翻页期间有新文件入库会重复或漏项。
- 做法:和群组历史一样改成 `(taken_eff, id)` 游标。

**D5 搜索更好用**(P2,1.5 天)
- 结果按相关度(FTS5 `bm25`)和时间混合排序;支持 `类型:视频`、`日期:2024-05`、`相机:iPhone` 这类过滤(PhotoPrism 的思路);EXIF 里的相机型号、镜头写进可搜索字段。

### 3.5 网络与通信(N)

**N1 远程访问:加一个点对点选项**(P1,文档 + 0.5 天)
- 现状:3.1.1 内置 frp,所有外网流量经 VPS 中转,带宽 = VPS 带宽(通常很小,是看视频卡的主要原因)。
- 做法:
  1. 文档 + 管理程序「内网穿透」页加一段说明:有条件的话装 **Tailscale**(或自建 headscale / NetBird),手机和 NAS 组网后大多数网络下能打洞直连,不经过 VPS;MediaHub 不用改,手机里加一个 `100.x.x.x` 的服务器地址即可(内网直连逻辑会把它当成一个候选地址探测)。
  2. 服务端 `/server/addresses` 把 Tailscale 网卡的地址也报出去(现在只报私网 IPv4 / 全局 IPv6),手机自动多一个候选。
  3. 只想要更省资源的中转:rathole 可以作为 frp 的替代"自定义命令"(已有自定义命令支持,写进文档)。
- 参考:Tailscale、NetBird、ZeroTier、rathole、frp xtcp(需要手机端也跑 frpc,不实用)。

**N2 列表接口条件请求 + 先显示旧数据**(P1,2 天)
- 现状:群组列表、历史页每次都完整返回 JSON(已 gzip)。经穿透时首屏要等一个完整往返 + 下载。
- 做法:
  1. 服务端给 `dialogs`、`history` 首页算 ETag(群组的 `gen` / 最后修改时间 + 用户状态版本 + 参数),带 `If-None-Match` 且没变时返回 304。
  2. 手机端把每个群组最近一次的首屏结果存到本地(DataStore 文件或一个小 SQLite 表),进入群组时**先显示本地的**,同时带 ETag 请求,304 就什么都不做,200 再替换。
- 参考:Telegram(先出本地缓存)、HTTP 缓存标准。

**N3 HTTP/3 / QUIC**(P2,先探测再决定)
- docs/12 里的结论仍然成立:先在测速页加"UDP 是否可用 / 丢包率"探测,数据说明值得再做。

### 3.6 手机端工程(A)

**A1 Baseline Profile + R8**(P0,1.5 天)
- 现状:`build.gradle.kts` release 里 `isMinifyEnabled = false`(注释说是为了崩溃堆栈可读),也没有 Baseline Profile。Compose 应用没有 Baseline Profile 时,首次启动和第一次滑动很多代码是解释执行 / JIT。
- 做法:
  1. 加 `androidx.profileinstaller` 和一个 `baselineprofile` 模块(Macrobenchmark),录"冷启动 → 打开群组 → 网格滑动 → 打开查看器 → 播放视频"这条路径,生成的 profile 随 APK 发布。
  2. 打开 R8(`isMinifyEnabled = true`,先不开资源压缩),补 keep 规则(kotlinx.serialization、JNI 的 LSFG 原生方法、反射用到的类);**每次打包保存 `mapping.txt` 到 `dist\mapping\<版本>\`**,崩溃日志用 `retrace` 还原——这样原来"堆栈可读"的顾虑就没有了。应用内导出日志时附上版本号方便对应映射文件。
- 收益(公开资料):Reddit 用 Baseline Profile + R8 full mode,冷启动整体快约 20%,首个 profile 覆盖的信息流启动中位数快 51%,ANR 减少约 30%。本项目以实测为准。
- 风险:R8 可能删掉反射 / JNI 用到的类 → 先在 debug 签名的 release 包上跑完整回归(播放、补帧、超分、本地模式、更新)。
- 参考:Now in Android、Mihon、Reddit 案例。

**A2 性能回归测试**(P1,1 天)
- Macrobenchmark 测冷启动时间、网格滑动的掉帧率(`FrameTimingMetric`);每次发版前在真机跑一次,结果记进 CHANGELOG 的开发说明,防止某个版本悄悄变慢。

**A3 列表与代码结构**(P2,2 天)
- `LazyColumn` / `LazyVerticalGrid` 的 `items` 加 `contentType`(图片 / 视频 / 日期分隔不同类型),复用更准确。
- 拆分 `VideoPlayer.kt`(1471 行)、`SettingsScreen.kt`(1245 行)、`VideoRenderer.kt`(1193 行):播放器拆成"状态 / 手势 / 顶栏 / 菜单",设置页一页一个文件。不改行为,只是以后改起来不容易牵一发动全身。
- debug 包加 LeakCanary 和 StrictMode(只在 debug,检查主线程读盘和内存泄漏)。

### 3.7 服务端工程与可观测性(O)

**O1 CI 与静态检查**(P1,1 天)
- 仓库是公开的,GitHub Actions 免费:每次推送跑 `go vet`、`go test`(Windows runner)、`staticcheck`、`govulncheck`(依赖漏洞)、`tsc --noEmit`、Gradle `lint` 和单元测试。**不在 CI 里签名 / 发布**(签名密钥只在本机)。
- 依赖升级用 Renovate 或 Dependabot 自动开 PR,CI 通过再合。

**O2 性能剖析开关**(P1,0.5 天)
- 管理端口(只监听回环)挂 `net/http/pprof`,管理程序「日志」页加"录 30 秒 CPU 剖析"按钮,结果打进诊断包。以后遇到"某个操作很慢"能直接看到时间花在哪,不用猜。参考 Syncthing 的 `STPROFILER`。

**O3 管理程序改事件推送**(P2,1 天)
- 现在各页 1~3 秒轮询一次(`Optimize.tsx` 1 秒、`Clients.tsx` 2 秒、`Tunnel.tsx` 2.5 秒、`Logs.tsx` 3 秒)。改成一个 `/api/v1/admin/events`(SSE 长连接),服务端有变化才推;页面切走就断开。管理程序本身空闲时 CPU 更低,状态也更及时。参考 Syncthing 的事件接口。

### 3.8 构建与发布(B)

已经做完的(见全局约定第 4 节):三端并行、`-Both` 一次出两套、Rust thin LTO、Gradle 配置缓存。剩下的:

- **B1 杀毒软件排除项**:把 `tools\cargo-target`、`tools\gradle-home`、`tools\gocache`、`tools\gopath`、`android\build`、`desktop\node_modules` 加进 Windows Defender 排除项(用户自己用管理员 PowerShell 执行 `Add-MpPreference -ExclusionPath <目录>`;只加缓存目录,不要加整个项目)。公开资料常见 20%~50% 的提升,以实测为准。
- **B2 日常调试用 debug 构建**:`build-android.ps1` 默认已经是 `assembleDebug`;只有打包才 `assembleRelease`。
- **B3 慢测试分组**:`internal/api` 里用真 ffmpeg 的测试(压缩、HLS)标 `testing.Short()` 跳过,日常 `go test -short` 只要十几秒,打包前再跑全量。

## 6. 评估过、不建议现在做的

| 方案 | 原因 |
|---|---|
| 换成 Jellyfin / Immich 当后端 | 本项目的核心是"文件夹即群组、只读原盘、Telegram 式界面";它们的库模型、写入方式(会在库目录写元数据)不符合"只写 .mediahub"的约束 |
| AVIF / JPEG XL 缩略图 | 和 docs/12 结论一样:编码慢或手机解码支持不全 |
| 把 libvips 用 cgo 编进服务端 | 项目坚持 `CGO_ENABLED=0`(纯 Go、便携);常驻进程的收益用"缩小解码 + EXIF 内嵌缩略图"基本能拿到 |
| Cloudflare Tunnel 承载视频 | 服务条款对大流量视频有限制,而且国内访问不稳定 |
| 在 CI 里签名并自动发布 | 签名密钥不能离开本机 |
| 端到端加密(Ente 那种) | 单用户局域网 + 自签名证书 + 指纹固定已经够;端到端加密会让服务端无法生成缩略图和转码 |
