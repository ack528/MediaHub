# 03 · 方案 B:完全自研服务端(MediaHub)+ 自研 Android 客户端

> **一句话**:不依赖 Jellyfin,自己写一个 Windows 服务,负责索引、缩略图、转码和 API;客户端用 06 号文档的统一架构,后端实现为 `backend-hub`。
> **定位**:可控性和格式覆盖最高,工作量最大。长期目标形态。方案 C 是它的"先借 Jellyfin 做视频"的分阶段版本,两者共用 07 号文档的 API。

## 1. 总体架构

```
┌──────────────── Android(06 号文档)────────────────┐
│ MediaBackend = HubBackend,只认 Dialog/Item/Playback │
└───────────────────────┬──────────────────────┘
                        │ HTTPS / HTTP2(Caddy 终结 TLS,或服务自带)
┌───────────────────────▼──────────────────────┐
│ MediaHub(Windows 服务,账户 svc-mediahub)               │
│ ┌────────┐ ┌────────┐ ┌──────────┐ ┌──────────┐ │
│ │ API 层   │ │ 认证/ACL │ │ 事件 SSE   │ │ 管理接口   │ │
│ └───┬────┘ └────────┘ └──────────┘ └──────────┘ │
│ ┌───▼──────────────────────────────────────┐ │
│ │ 索引器:目录遍历 + 变更监听 → SQLite(WAL,I:)        │ │
│ │ 分类 / EXIF / ffprobe / 稳定 ID                   │ │
│ └───┬──────────────────────────────────────┘ │
│ ┌───▼───────────────┐ ┌──────────────────────┐ │
│ │ 图片作业池(libvips…)   │ │ 视频:ffprobe/直放/remux/转码 │ │
│ │ P0..P4 优先级队列       │ │ 按需 HLS,片段缓存(K:)       │ │
│ └────────────────────┘ └──────────────────────┘ │
└───────────────────────┬──────────────────────┘
                        │ 只读
          C: D: E: F: G: H: I: K: L: M:
```

## 2. 技术选型

| 维度 | **C# / .NET(推荐)** | Go | Kotlin / Ktor |
|---|---|---|---|
| Windows 服务 | `UseWindowsService()` 内置 | 需 kardianos/service 等 | 需 WinSW/NSSM |
| HTTP/2、Range | Kestrel + `enableRangeProcessing` 现成 | 标准库 `ServeContent` 现成 | Ktor 需自写或插件 |
| 图片(libvips) | **NetVips**(自带原生库,无需 cgo) | CLI 调用或 cgo(Windows 上 cgo 配 libvips 麻烦) | 绑定较少 |
| NTFS 文件 ID / USN | P/Invoke 直接可用 | 同样可行(`golang.org/x/sys/windows`) | JNA,较别扭 |
| 子进程管理 | `Process` + Job Object | `exec.Cmd` | 同 |
| 单文件部署 | 自包含发布 | 单 exe,最简 | 需 JVM |
| 与客户端共享模型 | 否 | 否 | 是(可共用 `:core:model`) |
| 参考项目 | Jellyfin(同栈,可读其转码参数与 API 设计) | Photoview、Stash、go-vod、Memories | — |

**决策**:默认 **C#/.NET**(Windows 友好、NetVips 免 cgo、Jellyfin 同栈便于借鉴 ffmpeg 参数)。若你更熟 Go,可以用 Go,图片部分改为长驻的 libvips 辅助进程(`vips` CLI 池)。**无论哪种,对外 API 以 07 号文档为准。**

## 3. 索引器

### 3.1 哪些文件夹成为"群聊"
策略(可配置):
- **默认**:直接含 ≥1 个媒体文件(photo/video/gif/audio)的文件夹成为对话;仅含子文件夹的文件夹成为"话题容器"。
- **子文件夹模式**:`topics`(子文件夹是话题,默认)或 `merge`(父文件夹递归合并展示 `recursive=true`)。
- 排除规则:`$RECYCLE.BIN`、`System Volume Information`、`.thumbnails`、`@eaDir`、`Thumbs.db`、用户自定义 glob。
- 文件分类:按**扩展名**初筛,再用文件头魔数确认(防止后缀错误);未知类型归入 `file`。

### 3.2 扫描
- **首次全量**:每个 `io_group`(同一物理盘)独立一个遍历线程,并发数 1;`FindFirstFileEx(FIND_FIRST_EX_LARGE_FETCH, FindExInfoBasic)` 批量取目录项,尽量少触发属性读取。
- 第一阶段只写**文件系统级字段**(名称、大小、mtime/ctime、文件 ID),让对话列表几分钟内就能看到;第二阶段补 EXIF、尺寸、ffprobe 元数据;第三阶段才是 thumbhash 与缩略图。**用户不需要等全库完成才开始浏览。**
- **增量**:`ReadDirectoryChangesW` 监听目录变化(去抖 2 秒),并每日对每个根做轻量校对(比较目录 mtime)。大量文件复制时合并事件。
- **进阶(二期)**:NTFS **USN 日志**,可在不遍历整盘的情况下获得变更;枚举 MFT 需要卷句柄权限,与"低权限服务账户"冲突,因此做成一个只读元数据的小型特权辅助进程,仅在需要时启用。
- 指纹 `fingerprint = size + mtime + 头部 64KB 哈希`:相同则跳过重算,改名/移动靠文件 ID 保持稳定 ID。
- 坏文件:探测失败写入 `err`,在 UI 上显示占位,不阻塞队列。

### 3.3 元数据提取
| 类型 | 方法 | 说明 |
|---|---|---|
| JPEG/PNG/WebP/TIFF… | libvips 读头(宽高、方向)+ EXIF `DateTimeOriginal` | 只读头部,不解码像素 |
| HEIC/AVIF | libheif(经 libvips)读头 | 同上 |
| RAW | LibRaw / ExifTool 读 EXIF 与预览尺寸 | 不做去马赛克 |
| 视频 | `ffprobe -show_format -show_streams`,取 `creation_time` | 结果缓存于 `probe_json`,供播放决策 |
| 无拍摄时间 | 回退到文件修改时间 | 对话"时间"字段始终有值 |

## 4. 图片管线(尽量多格式)

### 4.1 输出规则
- 缩略图与大图转码一律输出 **WebP**(质量约 70,色彩转 sRGB,自动应用 EXIF 旋转),极个别需透明度的用 WebP lossless;为兼容极老机型可回退 JPEG。
- 档位固定 {128, 256, 512, 1024, 2048};`render` 最大 4096。
- **动图**:GIF/APNG/动态 WebP 的静态首帧用于缩略图;播放时服务端转为 MP4(H.264,无声,循环)或保留 WebP 动图,体积远小于 GIF。

### 4.2 解码回退链(按顺序尝试,成功即止)
| 格式 | 首选 | 回退 |
|---|---|---|
| JPEG | libvips **shrink-on-load**(解码时直接缩小,速度与内存最佳);小档位优先用 EXIF 内嵌缩略图(只读头部 ~64KB,对机械盘最友好) | ffmpeg 单帧 |
| PNG / WebP / BMP / GIF / TIFF / ICO | libvips | ImageMagick |
| HEIC / HEIF / AVIF | libvips + libheif | ffmpeg |
| JPEG XL | libvips + libjxl | ffmpeg / ImageMagick |
| RAW(CR2/CR3/NEF/ARW/DNG/ORF/RAF…) | **内嵌预览**(LibRaw `unpack_thumb` 或 ExifTool `-PreviewImage`) | libvips + libraw 完整解码(慢,仅在无预览时) |
| SVG | libvips + librsvg | ImageMagick |
| PSD / EXR / HDR / DDS 等 | ImageMagick | 通用图标 |
| 损坏/未知 | 通用文件图标,标记 `corrupt` | — |

### 4.3 沙箱与安全
解码器(尤其 libheif,上游维护者披露 2026 年已处理数十个安全公告)面对的是磁盘里的任意文件。
- 解码作业放进**独立低权限子进程**,限制内存与超时(例如 512MB / 20 秒),崩溃不影响主服务。
- 该子进程账户对媒体盘只读,对缓存目录只写其输出子目录。
- 定期升级 libvips / libheif / libde265 / LibRaw,订阅其安全公告。

### 4.4 磁盘友好
- 同一 `io_group` 同时只有 1–2 个读作业;机械盘上避免和视频直放争抢(视频直放走另一个更高优先级的"流"通道,不入队列)。
- 按需请求(P0)抢占后台作业(P3/P4)。
- 缩略图落盘:`I:\MediaHub\cache\thumb\{id低2位hex}\{id}_{w}.webp`,原子写入(先写临时文件再重命名),LRU 清理(上限默认 60GB)。

## 5. 视频管线

### 5.1 决策器
输入:`ffprobe` 结果 + 客户端 `caps` + 网络 `net` + 偏好。输出:`direct | remux | transcode`,并附 `reason`。
```
容器与视频、音频编码都在 caps 内,且码率 ≤ net.maxBitrate        → direct(Range 直放原文件)
视频在 caps 内,但容器不支持 或 音频不支持(DTS/TrueHD…)         → remux(视频 copy,音频转 AAC,输出 fMP4 HLS)
其它(视频编码/档次/分辨率/HDR 不支持,或码率超限,或用户选省流)  → transcode(按档位硬编/软编,必要时 HDR→SDR)
```
- 直放时服务端只做文件 Range 读取,**不消耗 CPU**;这是局域网下首选。
- 省流量(`lowdata`)强制 transcode 到低码率档。

### 5.2 按需 HLS(借鉴 go-vod 与 Jellyfin)
- `master.m3u8` 列出多档(例如 1080p≈4Mbps / 720p≈2Mbps / 480p≈0.9Mbps),各自的 `media.m3u8` 是**静态 VOD 列表**,总时长已知,播放器可立即拖动。
- **转码段**:强制关键帧 `-force_key_frames "expr:gte(t,n_forced*6)"`,每段 6 秒;**首段 2 秒**以加快起播。
- **remux 段**:视频 copy 不能随意切,按 `ffprobe -skip_frame nokey` 得到的**关键帧时间表**切段(目标 4–8 秒)。关键帧间隔过长的素材(例如 10 秒以上)自动降级为转码。
- 请求到达第 `n` 段:若该会话的 ffmpeg 正在向前产出且 `n` 在窗口内,则等待;否则**从 `n` 重启** ffmpeg(`-ss` + `-output_ts_offset`)。无请求超过 30 秒则杀进程。
- 片段缓存放 **K:\MediaHub\hls**,LRU,会话结束即清理;全局上限 50–100GB。
- 示例命令(NVIDIA;其它硬件见下表):
```
ffmpeg -hide_banner -ss {start} -i "{src}" -map 0:v:0 -map 0:a:{aidx}?
  -vf "scale_cuda=-2:720" -c:v h264_nvenc -preset p4 -b:v 2500k -maxrate 2800k -bufsize 5600k
  -force_key_frames "expr:gte(t,n_forced*6)" -c:a aac -b:a 128k -ac 2
  -f hls -hls_time 6 -hls_segment_type fmp4 -hls_playlist_type event
  -start_number {n} -hls_segment_filename "{dir}/seg_%05d.m4s" "{dir}/live.m3u8"
```
| 硬件 | 编码器 | 备注 |
|---|---|---|
| NVIDIA | `h264_nvenc` / `hevc_nvenc`;解码 `-hwaccel cuda` | 同时会话数受驱动限制 |
| Intel iGPU | `h264_qsv` / `hevc_qsv` | 集显服务器性价比高 |
| AMD | `h264_amf` / `hevc_amf` | Windows 上较可用 |
| 无 GPU | `libx264 -preset veryfast` | 1080p 实时需要较多核心,限制并发 |
- 编码参数、滤镜与 HDR→SDR 色调映射细节**直接参考 jellyfin-ffmpeg 的构建与 Jellyfin 的命令行生成逻辑**,不自己摸索。
- 其它:字幕提取为 WebVTT(文本字幕)或交由 mpv 渲染(ASS);多音轨以 HLS `EXT-X-MEDIA` 暴露;加密不做(局域网/VPN 场景,TLS 已够)。

### 5.3 并发与保护
- 全局转码并发上限(默认 2,依硬件调整);超限返回 `503 + 建议降档`。
- 转码进程用 **Windows Job Object** 管理(服务停止时整树清理),优先级设为 Below Normal,避免拖垮文件服务。
- 会话心跳 `progress` 每 10 秒一次;客户端崩溃后无心跳则自动回收。

### 5.4 封面、sprite、预览
- **封面**:`ffmpeg -ss {10%} -i src -frames:v 1 -vf scale=...` 输出 WebP;对 HDR 素材做色调映射;对黑帧检测重取一次(取 25% 处)。
- **sprite**(进度条预览):每 10 秒 1 帧、宽 160,拼成 10×10 的 JPEG 雪碧图,按需生成并缓存。形式参考 Jellyfin trickplay。
- **3 秒循环预览**:480p H.264 无声,约 100–200KB,按需生成,仅用于"可见时自动播放"。

## 6. 部署(Windows)

### 6.1 目录与账户
```
I:\MediaHub\bin         程序
I:\MediaHub\db          hub.sqlite(WAL)
I:\MediaHub\cache\thumb 缩略图缓存(LRU 60GB)
K:\MediaHub\hls         HLS 片段缓存(LRU 50–100GB)
K:\MediaHub\tmp         临时文件
```
- **不使用 C:**(仅 33.5GB 可用)和任何**媒体盘**(F:、G:、H: 几乎没有空间)。
- 服务账户 `svc-mediahub`:对各媒体盘 **只读 + 遍历**,对 `I:\MediaHub`、`K:\MediaHub` 读写。服务代码本身也**不包含任何写入媒体盘的逻辑**,双重保险。
- 以 Windows 服务运行,失败自动重启;日志滚动保存到 `I:\MediaHub\logs`。

### 6.2 网络
- 首选 **WireGuard / Tailscale 等私网接入**,服务只监听私网地址或经反向代理暴露。如要公网暴露,前面加 Caddy 终结 TLS(HTTP/2),并启用限流与 fail2ban 类封禁。
- 注意:部分内容分发型隧道服务对视频流量有使用条款限制,使用前先确认。
- Windows 防火墙只放行所需端口;管理接口只监听 127.0.0.1。

### 6.3 可观测性
- 指标:索引速率、队列长度、每盘 IO 利用、缩略图 p50/p95 生成耗时、缓存命中率、转码并发数、ffmpeg 失败率、HTTP 错误率。
- `/admin/index` 提供状态;日志结构化(JSON),便于排查。

## 7. 安全
- argon2id 密码哈希;登录限流;refresh token 轮换;设备管理与远程踢出。
- 路径与 ID:API 不接受路径,服务端规范化并校验根目录包含关系,拒绝符号链接与联接点逃逸;以只读共享读模式打开文件。
- 任何子进程参数用**数组传参**,不拼接 shell 字符串;文件名当作数据不当作命令。
- 子进程低权限、有限资源、有超时(见 §4.3)。
- 依赖更新与漏洞通告订阅(libheif、libvips、ffmpeg)。

## 9. 优缺点
**优点**:格式覆盖最全;API 完全按"聊天"语义设计(对话列表零 N+1、日期桶、`around` 跳转、ThumbHash);对磁盘的行为完全可控(只读、限流、不写媒体盘);无第三方服务的版本牵制。
**缺点**:工作量最大;**转码稳定性是最大的风险点**(各种奇怪的编码、音轨、字幕、时间戳),需要大量样本回归;需要自己维护 ffmpeg 与 libheif 的升级。
**缓解**:转码的命令行、滤镜、色调映射逻辑直接复用 jellyfin-ffmpeg 与 Jellyfin 的经验;视频先交给 Jellyfin(方案 C),B 的视频管线在后期替换。
