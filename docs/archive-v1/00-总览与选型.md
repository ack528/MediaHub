## 2. 从截图读出的环境事实与由此得出的约束

| 盘 | 总量 | 可用 | 状态 |
|---|---|---|---|
| C:(系统) | 118 GB | **33.5 GB** | 小系统盘,不能放缓存 |
| D: 数据10 | 2.72 TB | 138 GB | 将满 |
| E: 数据9 | 2.72 TB | 99.7 GB | 将满 |
| F: 数据8 | 2.72 TB | **180 KB** | 已满 |
| G: 数据7(NTFS) | 2.72 TB | **0 字节** | 已满 |
| H: | 2.72 TB | **652 KB** | 已满 |
| I: 数据 | 465 GB | **200 GB** | 有余量 |
| K: 数据 | 465 GB | **339 GB** | 有余量 |
| L: 数据 | 2.72 TB | 244 GB | 较满 |
| M: 数据 | 2.72 TB | 56.5 GB | 将满 |

由此得出的**硬约束**(已贯穿各方案):

1. **所有写入只发生在 I: 和 K:**:数据库、缩略图缓存放 I:;HLS 片段与转码临时文件放 K:。C: 和其它所有盘都不放生成物。
2. **媒体盘一律只读**:F:、G:、H: 本就写不进去,任何"把 NFO、trickplay、封面写回媒体旁"的功能都会失败甚至死循环(jellyfin#18152)。服务账户设**只读 ACL**,代码本身也不含写媒体盘的逻辑。这同时保护你的数据不被软件 Bug 误伤。
3. **不能预转码或复制**:满盘意味着没有空间存放转码副本。只能**按需转码 + 缓存可淘汰**。
4. **机械盘的随机读很弱**(2.72TB 级大概率是 HDD,型号待确认):索引、缩略图、转码都要按物理盘限流(每盘并发 1–2),用户请求优先于后台作业,后台作业尽量放夜间。
5. **盘符可能变化**:用**卷 GUID + NTFS 文件 ID** 作为稳定标识,盘符只当显示名。
6. **规模假设**:总容量约 20TB 级,文件数可能是百万到数百万。设计目标按 **500 万条目**;容量估算见 07 号文档 §5。

## 3. 方案对比

| 维度 | A 纯 Jellyfin | B 全自研 | **C 混合(推荐)** | D 改造 Telegram |

| 日期桶、跳转、自然排序 | ✗ | ✓ | ✓ | 部分 |
| 视频转码稳定性 | ✓ | 风险最高 | ✓ | 需另造 |

## 4. 推荐路线

```
Phase 0  PoC(约 1–1.5 周)      → 验证关键假设,决定 A 的取舍
Phase 1  方案 C 的 M1+M2(约 9 周) → 第一个可日常使用的版本(图片 + 直放视频)
Phase 2  方案 C 的 M3+M4(约 8 周) → 视频转码/省流量 + 格式与排序补全
Phase 3  M5 与长期             → 稳定性、安全、监控;视情况实现 FfmpegEngine 向 B 演进
```
A 不作为终点,但它的 Jellyfin 视频链路验证**直接复用**到 C 的 `JellyfinEngine`。

## 6. 需要你确认的问题(影响细节,已给出默认假设)

| 问题 | 默认假设 | 影响 |
|---|---|---|
| 手机访问服务器的方式:仅局域网、VPN(WireGuard/Tailscale)还是公网? | 局域网 + VPN | 决定带宽策略、TLS 与暴露面 |
| 服务器 CPU / 显卡型号? | 未知 | 决定转码并发与编码器 |
| Windows 上是否已有 Jellyfin? | 没有 | 影响 PoC 起点 |
| Android 最低版本、手机型号? | Android 8+ | 影响 `minSdk` 与硬解能力 |
| 是否需要多人使用/权限隔离? | 少量家人使用 | 决定是否启用 ACL |
| "文件"(文档、压缩包)与音频是否也要在对话里展示? | 展示音频与文件,默认不显示 | 影响索引范围 |
| 会不会分发 APK(上架/发给他人)? | 仅自用 | 影响 GPL/LGPL 取舍 |
| 子文件夹默认"话题"还是"合并展示"? | 话题,可切换 | 影响对话数量与列表层次 |
| 媒体中是否有需要隐藏/加锁的文件夹? | 无 | 是否做应用锁与隐藏分区 |
