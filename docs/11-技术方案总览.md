# 11 · 技术方案总览(当前版本)

> 写于 2026-10-12,对应手机端 2.16.0 / 服务端 1.9.0。其它文档(00 ~ 10)是设计过程和各版本的变更记录,这一篇是"现在的实际方案"。

## 1. 项目是什么

把 Windows NAS 上的"盘符 / 文件夹 / 媒体"在 Android 手机上呈现成 Telegram 式的聊天:一个母文件夹是一个群,里面的图片和视频按时间或文件名排成消息流或网格。

| 部分 | 技术 | 作用 |
|---|---|---|
| 服务端 MediaHub(`server/`) | Go、纯 Go SQLite | 索引、封面、转码、账号、更新 |
| 管理程序(`desktop/`) | Tauri 2(Rust + 网页界面) | 媒体库、缓存、转码、账号、日志、软件更新 |
| 手机端 LocalBrowse(`android/`) | Kotlin、Jetpack Compose、Media3 | 浏览、播放、画质增强 |
| 检测程序(`probe/`) | 独立 Gradle 工程 | 手机 GPU / LSFG 实测、回放录制、超分评测 |

约束:只在局域网、最多 2 台设备、不考虑并发、全部工具链放在项目文件夹里。

## 2. 整体架构

```
手机(Compose / Coil / Media3)
   │ HTTP(S) 局域网,Bearer 令牌
   ▼
MediaHub 网关(Go,Windows 单 exe)
   ├ 索引器 → SQLite(WAL + FTS5 trigram)
   ├ 原图 Range 直出 / 格式转换(render) / 视频封面
   ├ 内置 HLS 转码(ffmpeg,按需分段)
   │    └ 可选委托 Jellyfin(仅转码,Intel QSV)
   └ 每盘缓存 X:\.mediahub\(配额 + LRU)
```

## 3. 服务端(`server/internal/`)

| 包 | 职责 |
|---|---|
| `index`、`classify`、`natsort`、`winfs` | 扫描(三阶段:目录 → 元数据 → 细节)、文件夹归群规则、自然排序、NTFS 文件 ID 与读取失败分类 |
| `meta` | ExifTool / ffprobe 元数据、MP4 / MOV 结构完整性检查(识别 0 字节、截断文件) |
| `store` | SQLite 模式与迁移(`roots`、`dialogs`、`media`、`users`、`tokens`、`user_dialog`、`cache_entries`、`user_view`、`user_playback`、`kv`) |
| `api` | HTTP 接口、原图直出、`render`、封面、HLS、随机浏览、用户状态同步、管理接口 |
| `cache` | 每盘缓存目录、配额、LRU 清理 |
| `jellyfin` | 可选的 Jellyfin 委托与管理 |
| `auth`、`tlsx` | 账号 / 令牌、HTTPS |
| `logx`、`update`、`proc` | 日志与崩溃报告、自动更新(`apply.ps1` 替换并重启,失败回退)、进程管理 |

**图片**:只用原图,Range 直出,手机端降采样显示。手机解不了的格式(HEIC / RAW 内嵌预览 / TIFF 等)走 `/media/{id}/render` 转 JPEG。

**视频**:封面由服务端生成。手机能直放的直接放;不能放的走 HLS:先按总时长生成完整播放列表(固定 4 秒一段),段在请求到时才由 ffmpeg 现转,拖动进度条就从该段重新启动 ffmpeg;转码进度领先播放位置约 3 分钟就暂停。转码只调码率,不缩放分辨率。

**接口**(`/api/v1/`):`server/info`、`auth/login|logout`、`dialogs`(含 `history`、`buckets`、`view`、`state`、`topics`)、`search`、`random`、`media/{id}/file|poster|render|hls|playback`、`state/views|playback`、`admin/*`(状态、重扫、更新、日志;只接受本机回环地址 + 管理密钥)。

**同步**:浏览位置(排序、网格或聊天、列数、过滤)和视频播放进度按用户存在服务器上,换设备能接着看;冲突以最后更新时间为准。

## 4. 管理程序(`desktop/`)

Tauri 2。托盘(启动 / 停止服务、重新扫描)、开机自启(写当前用户 Run 注册表项)、防火墙检测与一键放行、索引进度、缓存占用、账号、日志(过滤、搜索、导出脱敏日志包)、软件更新。

## 5. 手机端(`android/app/src/main/java/com/localtg/`)

| 目录 | 内容 |
|---|---|
| `data/` | API 客户端、设置(DataStore + JSON,新增字段都有默认值)、会话与令牌(Keystore AES-GCM)、本地媒体、自动更新、保存到相册 |
| `ui/` | 群组列表、聊天流 / 网格、查看器、随机浏览、搜索、设置、播放器及面板、Telegram 风格主题 |
| `render/` | 画质增强渲染器(下一节) |

两个设计要点:
- **两种数据源共用一套界面**:本地媒体模式用 OkHttp 拦截器伪装成服务端接口(含随机、重新洗牌),界面代码不分叉。本地库只在 MediaStore 真的变化时才重读,并发请求共用一次读取,缩略图解码限流。
- **多服务器**:可保存多个服务器,一键切换。

## 6. 画质增强管线(`render/`)

```
ExoPlayer → SurfaceTexture(OES) → RGBA16F 纹理
   → [有效清晰度检测] → [超分着色器链] → 帧环(5 帧)
   → [LSFG 帧生成(Vulkan,异步线程)]
   → 按屏幕 vsync 选帧(相位累加器)→ [SDR→HDR] → 上屏
```

### 6.1 超分

- **运行时**:自己实现了 mpv 用户着色器的最小运行时(`MpvShader.kt`:`//!HOOK / BIND / SAVE / WIDTH / HEIGHT / WHEN`,LUMA / MAIN 钩子,逆波兰表达式),直接运行开源着色器。不支持计算着色器和 LUT。
- **算法**:FSR 1.0(AMD,通用)、Anime4K 小 / 中(动画)、FSRCNNX 小 / 中(真人 / 影视,LGPL-3.0,独立文件 + 许可证说明)。
- **门槛**:着色器自带"输出不到源的 1.2 ~ 1.3 倍就跳过";分辨率上限默认 1080p;处理耗时连续约 2 秒超过帧间隔的 90% 自动停用,换算法或改上限后重新判断。
- **有效清晰度检测**(`Sharpness.kt`):GPU 上在 16×9 个小块取规则格点,比较相邻 1 像素与相隔 4 像素的亮度差平方和之比 R(清晰约 0.33,糊到 3 倍以上约 0.08)。每 24 帧测一次,EMA 平滑、连续两次同档才切换。判成偏糊就先把源帧按盒式滤波缩到有效分辨率,再进着色器链,上限也按有效分辨率判断。缩小滤波必须是干净的盒式,早期错位的 4×4 样点多糊一圈,超分几乎白做。
- **实测**(模拟器,同一段真人画面造的"标称 1920×1200 实际 1/f 清晰度",对高清原片的 PSNR):1/2 清晰度 26.7 → 27.9 dB,1/3 清晰度 24.2 → 24.6 dB,1/4 几乎无提升,本来就清晰的画面逐位不变。

### 6.2 补帧(LSFG)

- **来源**:Lossless Scaling 的帧生成算法(lsfg-vk 的 framegen:mipmaps → alpha → beta → gamma → delta → generate)。着色器运行时从用户自己的 `Lossless.dll` 提取,发布版不带 DLL。
- **GL ↔ Vulkan**:AHardwareBuffer 共享同一张图,不拷贝。
- **Mali 修正**:Mali 驱动(r54p1)对 SPIR-V "OpImageSampleExplicitLod + ConstOffset" 算错,光流全错。`spvpatch.cpp` 在加载着色器时把偏移换算进坐标,只对 vendorID 0x13B5 启用。同时修了 framegen 要"光流比例的倒数"而我们传了比例的问题。
- **适配与降级**:优先 FP16 着色器,失败退回 FP32;跟不上时依次降光流精度、减半生成倍数、降输入分辨率,最后停用。
- **上屏节奏**:相位累加器(锁相环思路)对齐 vsync;会话在需要补帧时才创建,"不需要"要持续 5 秒才释放(vivo 会把屏幕在 120 / 60Hz 之间切换);按视频声明的帧率定倍率,不用到达间隔估计。
- **验证方法**:`probe/` 里的真值片段(240fps 渲染后每 10 帧取 1 帧,中间帧当标准答案)+ 电脑模拟器(宿主 Intel GPU)当参照 GPU,输入输出走 Vulkan 直传、逐级中间图像比对;修复后 Mali 与 Intel 输出平均差 0.05/255。详见 `docs/10-天玑GPU检测报告.md`。

### 6.3 SDR 转 HDR

BT.2020 PQ 的 10 位 EGL 表面 + 窗口颜色模式 HDR。逆色调映射:参考白 203 nit 不动,亮部从伽马亮度 0.35 起平滑拉高(指数 1.5),到纯白达到设定峰值(默认 600 nit),大面积亮区只压低到 40%。HDR 表面只在渲染器创建时决定,播放中开关「SDR 转 HDR」会重建画面视图。

### 6.4 其它

- `HighRefresh.kt`:强制屏幕保持同分辨率下 ≥ 120Hz 的最高档。
- `HardwareProbe.kt`:离屏 GL 实测各超分算法耗时,按占 30fps 帧间隔的比例判定并推荐设置。
- `FrameRecorder.kt` + `FrcTrace.kt`:内录上屏帧、补帧详细日志(调试用)。

## 7. 构建、发布与测试

- **便携工具链**:`tools\` 下是 JDK、Android SDK / NDK、Go、Rust、Gradle、ffmpeg、Jellyfin 等,`env.ps1` 重定向所有缓存目录。构建时把项目根目录映射成盘符 L:(CMake 处理不了中文路径)。
- **打包**:`tools\package.ps1`。自用版 APK 带 Lossless.dll,`-Release` 版不带,另出自动更新用的 zip。**手机版本号要手动改 `android/app/build.gradle.kts`**,脚本的 `-Version` 只管文件名。
- **发布**:`tools\publish-release.py` 推 GitHub(ack528/MediaHub),本地 master 推到远端 main。
- **检测程序**:每个测试在独立进程里跑,崩溃只记录;回放测试复用主程序同一套渲染代码并录下上屏帧。超分 / HDR 评测流程:`tools\tmp\make_sr_testset.sh` 造测试片、`run_sr.sh` 跑模拟器、`score_sr.py` 对真值打 PSNR 和锐度。模拟器要过滤 goldfish 硬解,`probe/app/src/main/assets/shaders` 要从主程序复制(已 `.gitignore`)。

## 8. 已验证并放弃的方案

| 方案 | 结论 |
|---|---|
| 运动补偿 / 混合 / OpenCV 光流补帧 | 早期做过,1.12.0 全部删除,只保留 LSFG |
| RIFE(手机 ncnn Vulkan) | 天玑 9500 上约 35 ~ 435 ms / 帧,fp16 无提升,做不了实时,已删除相关代码和工具链 |
| 高通 QAIRT / SNPE / QNN | 只能高通 NPU,用户手机是联发科,已删除 |
| 联发科 NPU 补帧(NeuroPilot) | 补帧网络里的 warp 算子 NPU 不支持,没有集成 |
| 厂商系统级补帧(独立芯片 / MFRC / MEMC) | 没找到向第三方开放的接口 |
| 解码器运动矢量 + NPU(ANVIL 一类) | 只支持 H.264 软解、画质不及 RIFE,没有集成 |
| ArtCNN 超分 | 计算着色器,运行时不支持 |
